# Changelog

All notable changes to Ridge will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- The standard-library `Error` can be printed. `Err e -> $"failed: ${e}"` is the most ordinary line anyone writes with one — `Error` is the failure half of every capability-bearing `Result`, from the file verbs to the data layer — and it was `T029 no instance ToText Error`, with no way out from the reader's own workspace: the type is declared elsewhere, so it takes no `deriving` clause of theirs, and an instance of their own would be an orphan. The only route through was to know a field name and interpolate that instead. Checking a corpus of twelve local projects, seven of the ones that failed to build failed on this shape and nothing else. An error now renders as `code: message` — `enoent: no such file or directory` — with the classifier first, because an interpolated error ends up in a log line and the code is what identifies the failure there; it is also the channel the standard library itself sorts on. Rust, Python and Java all keep the classifier alongside the human text for the same reason. Either half is dropped along with its separator when empty. The rendering is written in Ridge, in a new `std.error` module, rather than as a runtime helper: nothing about it is a property of the host, and putting it in the shim would mean a second backend reimplementing how an error prints. `Error` joins the pure-data modules that already carry a prelude alias, so `Error.toText e` also works with no import.
- Two of the eight built-in `ToText` instances had no dictionary. `Decimal` and `Uuid` interpolate fine, and a `where ToText a` function called at either failed to build with `E001: Local symbol '$inst_ToText_Decimal' not found`. When the built-in instances started being synthesised at the use site, those two were left out on the stated theory that they carry a real instance of their own; they do not, and for the same reason the others do not — being seeded as prelude instances is exactly what stops a constant from being generated for the standard library's own `toText`. So the synthesis declined and the fallback named a constant nobody emits. Both are in the set now, and the set and the per-type conversion are read off one table instead of being stated twice, which is what let them disagree. The test that would have caught it has to run the program: all of these type-check clean either way, and the original covered the two types a literal can produce.
- A function constrained by a class with more than one parameter compiles. It aborted the compiler instead — `fn go (x: a) -> b where Pairable a b = wrap x` type-checked and then hit an assertion in lowering, because asking a two-variable constraint for its only variable is a contradiction and three places were asking. Two of them were not about naming at all: one looks a caller's dictionary up by matching a constraint against a variable, which now asks whether the constraint ranges over it rather than whether its single variable equals it, and one reads the concrete type a call pinned the constraint to, which now takes the first variable the call actually pins — the determining one first, for a class with a functional dependency. The third is the name of the parameter that carries the dictionary, and six sites across four files were building it by hand from the constraint's first variable; they go through one function now, because the site that declares the parameter and the site that looks it up have to agree exactly and nothing was holding them together. A single-parameter dictionary is still spelled `$dict_ToText_3`, byte for byte, so nothing that already resolves moves. Release builds did not abort — the assertion is compiled out there — and, measured rather than assumed, they also did not dispatch wrongly: two instances of a two-parameter class reached the right method before this change as well.
- A record literal built from a standard-library record type has its fields checked. `Response { status = "not an int", body = 42 }` compiled clean, and so did an unknown field name and a missing one: the importing module resolved `Response` to a stub with no schema behind it, and the record path, finding nothing to check against, dropped the whole field list without looking at it. Five of the eleven public record types in the standard library were in that state — `Request`, `Response`, `Parsed`, `Output` and `Duration` — while the other six were fine, which is what made it invisible. Two causes, not one: three of the five had no declaration the compiler could see at all, and the other two were built in but unreachable, because the table that resolves an imported standard-library type name listed four names by hand and dropped everything else. The table is now built by scanning what the compiler declares, so it cannot fall behind again, and a test asserts that every `pub type X = { … }` in the standard library is reachable — it fails on a new one the moment it is added. The visible symptom was narrower and stranger than the hole: an interpolation in one of those fields reached lowering with no type for its hole and was passed through unconverted, so an `Int` hole rendered as whatever byte it happened to be, or crashed.

- `T001` names the two types the right way round in every position. Five of the nine places it can be reported from had the pair reversed — record construction, `with`-update, `return`, a list element and a `match` arm all said `expected Text, got Int` for a field declared `Int` and given a `Text`, which reads as an instruction to change the declaration rather than the value. `unify` reports its first argument as the expected one and those five passed it second. The same reversal was found and fixed in the `let` position earlier; that investigation sampled three positions, found two of them correct, and concluded a single call site was at fault. Probing all nine is what turned up the other five. The regression test asserts the orientation rather than the code, because a reversed pair still produces a `T001` and every test that checks only for the code went on passing for the two months this survived.

- A lambda is its own return boundary, and its declared return type means something. `guard … else return` inside a callback was checked against the return type of the function containing the callback, not the callback's own — so a handler returning `Response`, written inside a function returning `Result Unit Error`, was told it should have returned the latter. `?` inherited the same target, for the same reason: it lowers to `return Err e`. Code generation had never agreed with either of them, giving every lambda a catch frame of its own since the feature landed, so the throw has always been caught at the lambda and the checker was alone in thinking otherwise. It stayed hidden because the two return types usually coincide — a codebase threading one `Result` through a call chain never sees it. Alongside that, the return type an author writes on a lambda now reaches the compiler at all: `fn (n: Int) -> Text = n` was parsed, discarded before the AST was built, and therefore never compared with anything, which made `fn (s: Text) -> Int = "clearly text"` a clean build. The rule the three layers now share is written down in the specification rather than left to be read off one backend, and the grammar records the `fn params -> Type = body` form it had been accepting without describing.

- `Int.wrappingAdd` wraps, and `Int.saturatingAdd` clamps at both ends. Neither did. Both are written against the 64-bit boundary, and both spelled that boundary with literals the compiler could not hold — `-9223372036854775808`, whose positive half is one past the maximum, and 2^64 for the wrap modulus. Each became zero, so `wrappingAdd` subtracted nothing and returned the un-wrapped sum, and `saturatingAdd` clamped a negative overflow to `0` instead of the minimum. `saturatingAdd maxVal 1` was right, which is the sort of half-working that keeps a bug alive; its own test asserted the low clamp against the same zeroed constant, so a broken function and a broken expectation agreed and the suite stayed green. The boundary values are now computed from `Int`'s maximum rather than written down, which is exact at run time, where integers are arbitrary-precision.

- An integer literal too large for `Int` is an error instead of a zero. `99999999999999999999999999` compiled clean, ran, and printed `0` — not a wrap, which would have given `-9223372036854775808`, but a substitution, with `check`, `build` and `run` all reporting success over a program whose numbers were not the ones written. The compiler had in fact diagnosed it: the literal parser pushes `L110` and returns zero from the same arm, so the zero was the diagnostic's own footprint. Nothing collected it. Lowering had built diagnostics since the phase existed and no caller had ever read them — the context accumulated them, was consumed, and dropped them; no field carried them out of the crate; there was no `LowerError` adapter beside the six that exist for the lexer, parser, resolver, manifests, types and codegen. All thirteen codes are now delivered, `L101`–`L110` plus `L997`–`L999`, the last of which is how the compiler reports a violation of its own invariants. Their messages were written for whoever was reading a debug log — each repeated its own code and appended the `Debug` of a span, both of which the renderer already supplies — and are now written for the person who has to fix the program. A float literal that is not finite is caught in the same place, as `L111`: Rust's parser answers `Ok(inf)` rather than failing, so `1.0e400` used to reach codegen and be refused there in terms belonging to Core Erlang.

- A `where` clause no longer has to repeat what the class declaration already says. `class Describable a where Named a` states that every `Describable` is a `Named`, and that rule is enforced when an instance is declared — but a body calling `name` under `where Describable a` was told it was missing a constraint, with `T055` naming a clause the class had already implied. The test asked only whether the class appeared in the list the author wrote, and never followed the superclass edges the class table has been carrying all along. It now walks them, so a promised subclass supplies its superclasses, while a class that is neither promised nor inherited is still reported as before. Three positions shared that too-narrow test — a parametric instance's element, a signature variable's dictionary, and the promise check itself — and all three follow the same rule now.

- A helper declared inside a function can be used at two types, and one that promises a class is handed the dictionary. `fn firstOr (fallback: a) (xs: List a) -> a`, written next to the three lines that need it, was rejected at its second use — except when its body happened to be a `match`, which accepted it and ran it correctly, so whether a local helper was generic turned on a detail of how its body was written. Under a `where` clause the failure moved rather than disappeared: the program compiled clean and died running, since the lowering had no notion of a dictionary for a local helper, and an unresolvable dictionary falls back to a placeholder that arrives in the body as the atom `ok`. A helper's signature is now read the way a top-level declaration's is — one variable per name, held rigid, and the body checked against it rather than choosing it — and the classes it promises are declared as dictionary parameters and passed at each call, so two calls at two types reach two instances. A signature that is short a promise reports `T055` naming the `where` clause to add, and one whose body does not meet it reports the mismatch against the signature, in that order; the raw form stated the two the other way round.

- A constrained function can pass its own type variable to a parametric instance again. `fn twice (x: a) -> Int where Weigh a = weigh (MkPair x x)` was rejected with `T030 ambiguous constraint`, pointing at a variable that is not ambiguous: `twice` promises `Weigh a`, so the caller hands that dictionary in and `Weigh (Pair a)` builds its element dictionary from it. The sub-dictionary resolver had an arm for a concrete head and one for a type variable, and none for a signature variable, so the promised one fell to a placeholder that forwards a sentinel — which the ambiguity check then read, correctly, as an element nobody could supply. A signature variable now forwards the variable it was minted from, the same name the incoming dictionary parameter is declared with. Where the signature makes no such promise, the answer is `T055` naming the `where` clause to add, rather than an ambiguity that sends the reader after a type annotation which would fix nothing.

- Building in a directory that has not been built in before no longer recompiles the whole standard library. It was rebuilt per output directory: the reuse check was already careful — a manifest, written by this compiler version, naming modules all present and no older than the compiler binary — but the artefact it guarded lived under `<workspace>/target/`, so the answer was `false` for every new one. The stdlib belongs to the compiler rather than to the directory that needs it, and now lives once per compiler under the user cache, keyed by version and by the compiler binary's own timestamp. A published directory is therefore never mutated: a rebuilt compiler writes a different one instead of over the old, so no reader can meet a half-written set and a stale answer would have to sit at a key nothing asks for. Measured on four consecutive fresh workspaces: 24.0s, then 4.6s, 4.5s, 4.4s. The test suite pays this 252 times.

- A `where ToText a` function can call another one at a built-in type. `if pick then describe x else describe 7` failed to build with `E001: Local symbol '$inst_ToText_Int' not found`, because no such constant exists: interpolating a built-in lowers straight to `std.int.toText` and never asks for a dictionary, so none was ever emitted. Two families were already handled this way — the prelude `Encode`/`Decode` instances and the built-in `Ord` ones, both synthesised inline at the use site — and the built-in `ToText` instances are the third. `Text` renders through its dictionary as itself, which is the arm most easily written as something else and never noticed, since the value already looks right.
- A function with a `where` clause no longer hands its own dictionary to a call that named its type. `fn twoDicts (x: a) (pick: Bool) -> Text where Show a = if pick then describe x else describe MkTag` compiled clean and then reached the wrong instance method: `describe MkTag` was given the `Show Color` the caller had supplied, so a `Tag` arrived in `colorToText`. Two dictionaries of one class in one body was the whole requirement — no recursion, no generic container, no parametric instance — and what kept it alive is that the existing coverage put the static call site and the forwarding one in separate functions. Underneath it, a class method that dispatches on its arguments was being resolved from the type of its result whenever no argument was concrete: `compare (x: a) (y: a) -> Ordering` inside a generic `sort` pinned `Ordering`, which has an `Ord` instance of its own and so looked like an answer. Choosing a dictionary compensated for that by ignoring any pin that was not a type variable, which is why the first form was wrong and the second worked. A pin now records whether the class variable was actually located, so only a call that named the type it meant outranks the caller's dictionary.
- `T010` names types instead of the compiler's own counters. It printed `cannot unify ?65 with #6 (?63)` — two unification-variable numbers and an index into the type-constructor table, none of which the reader wrote or can look up. It now says `` `a` would have to contain itself: `List a` ``, using the same letters the language server already shows on hover. The two sides are named in one pass, so the variable reads as the same letter on both; naming them separately, or before resolving them, produced `` `a` would have to contain itself: `List b` `` — a sentence the type beside it disproves. The headline dropped "occurs check failure" as well: that is the name of the step the compiler was performing, not of the reader's problem.
- Two more diagnostic codes are retired, and this pair was nearly wired instead. `T008` and `T012` were counted as unfinished work on the strength of their wording; run against the compiler, both turned out to be answered already, and answered better. A misspelled constructor never reaches the type checker — `R010` rejects the name and carries the same did-you-mean — and a constructor that exists but belongs to another type is a plain mismatch naming both types, which `T008` would have called unknown. `T012` is the sharper case: it says only built-in types and records of built-in types can be interpolated, which stopped being true when `ToText` became an open class in 0.2.13. What arrives instead is `T029`, naming the type and the two ways to give it an instance. Wiring `T012` would have published a rule the compiler no longer enforces. Both keep their number and their page, and `ridge explain` answers for them with the code that arrives in their place.
- A type alias that resolves to itself is rejected. `type A = A`, `type A = B` paired with `type B = A`, and `type A = List A` all type-checked clean: an alias stands for something else, and each of these stands for nothing. The cycle was already being found — the expansion pass has always carried a stack to stop itself looping — and then discarded without a word, so the first error the author saw named a type no value can have. It now reports `T011` with the ring written out, `A -> B -> C -> A`, one diagnostic per cycle rather than one per alias on it. A union may still refer to itself, which is how a tree is declared. The claim that the grammar prevents this, repeated in a source comment, the emission census and the `T011` fixture, was never true.
- A pattern that does not fit the scrutinee says which side is which. Matching an `Int` against `"text"` reported `expected Text, got Int` — the scrutinee is what sets the expectation, so the two were named the wrong way round, and neither was labelled as the pattern. It now reports `T007`: expected `Int`, but pattern implies `Text`. List and cons patterns against a non-list scrutinee say what the pattern implies rather than leaving it to be worked out, and a tuple pattern of the wrong length keeps the message about length — which also stopped counting the two sides backwards.
- A call that passes the wrong type says which argument it was. `f 1 "x" 3 "four"` reported a bare `expected Int, got Text` with the whole call underlined, leaving the reader to work out which of the four produced it — and the compiler knew: it checks a call by comparing the two function types in one step, which stops at the first bad parameter holding neither its position nor its span. The mismatch is now reported against the argument itself as `T002`, naming the callee and the position, and every argument that does not fit is reported instead of only the first. A partially applied call reads the same way. Both used to state the two types the wrong way round — `add "text"` said `expected Text, got Int` when the declaration is what the argument had to meet. `add(1, 2)` still gets the hint teaching that Ridge calls are space-separated, which is worth more to whoever wrote it than an argument index.
- Three diagnostic codes no program could produce are retired. `P018` rejected a record pattern written without a leading constructor name, which became legal in 0.2.12 — the failure it reported stopped being one. `C003` and `M012` both reported a dependency cycle, one from the driver and one while reading a manifest; a manifest is read on its own and never sees a cycle, and the package layer resolves the whole graph and reports `P206` with the path it found. All three keep their number and their page, and `ridge explain` still answers for them. One type error in the same count is not retired, and has since been wired instead: `T013` — see the polymorphic-recursion entry under Added.
- `ridge run` shows the warnings the compile produced. The same source that `ridge check` reported `T017` on ran with no diagnostic at all: the compile stopped on errors and dropped everything else on its way to launching the program, so a lint stayed invisible for as long as someone developed with `run` and turned up as a surprise from CI. Warnings now print before the program starts, and still do not stop it — `run` is not a build gate and takes no `--deny-warnings`. `run --observer` and `run --watch` already printed what they found; plain `run` was the last of the three that compile to disagree.
- A diagnostic code that stops being emitted is retired rather than deleted, and its number is never reused. Three published statements about what a code promises disagreed with the compiler and with each other: the rustdoc on every `code()` said codes were stable across releases without naming one, in ten places across six crates, while the roadmap already scoped that promise to 1.0 — so the compiler's own source was the thing making a promise nobody had made. Codes are stable from 1.0; before then a code that is wrong, such as one colliding with another crate's, can still be renumbered. `ridge explain` now answers for a retired code with the code that arrives in its place, and `docs/diagnostics.md` keeps its heading, because the number in an old log or a CI filter is the only handle its reader has and the editor's diagnostic link is built from the code alone. `C402` is back under that rule, pointing at `C004`. The roadmap's namespace map is corrected too: it was right in two rows of seven, missed the `E` family entirely, and claimed an `L8##` range for the language server that does not exist. The letter says which phase a reader is in, not which crate to open.
- Every test `ridge test` refuses to run now says which rule it broke. Three rejections reached the terminal as hand-written lines that bypassed the error type owning them, and one of the three carried no code at all — nothing to search for, nothing to hand to `ridge explain`. A test whose return type is not `Result Unit Text` reports `C305`, and one that declares no return type at all reports `C306`, which used to arrive as `C305`'s message telling a signature its return type was unsupported when it had not declared one. Neither message offers `Bool` as the alternative: it still works, but `C303` deprecates it in the same run, and one message should not push what another is retiring. The two test advisories also print as one line again — `C303` and `C304` had a run of source indentation baked into their text.

### Added

- A function whose signature annotates every parameter and the return type may call itself at a different type. That is what a non-regular datatype needs to be traversed at all: `type Nested a = Flat a | Deep (Nested (List a))` has a `depth` whose recursive call receives a `Nested (List a)` where the signature says `Nested a`, and until now the compiler rejected it — first as an infinite type, later as an argument mismatch, both of them describing a program the author's own signature accepts. There is no verbosity that got around it. Each recursive occurrence now instantiates the declared type afresh, which is the rule Haskell and OCaml settled on for the same reason: inferring such a type is undecidable, but checking one that has been written down is not. It only ever accepts more, because the body is still held to the signature — in `fn g (x: a) -> a = g 1` the recursive call returns an `Int` where `a` was promised, and that is now a mismatch at the declaration rather than a surprise for the first caller. A signature that leaves a position off keeps the ordinary rule, and a recursive call at a second type under one reports `T013`, which names the annotations that would lift it instead of blaming the argument. That code had been carried unemitted since 0.1.0 for the case that no longer exists; the case that does is this one.
- `ridge explain <CODE>` says what a diagnostic code means. Until now the code printed next to an error was a dead end: the meaning lived in the source of whichever crate declared it. All 242 codes the compiler can emit now carry a line saying what went wrong and which part of the compiler reports it, and this is the command that reads it back. `ridge explain T031` answers, and so do `t031` and the `[T031]` that a copy-paste off the terminal actually produces; `ridge explain --list` prints the whole table; and it needs no project around it, since the moment you most want to look a code up is while your workspace is the thing that is broken. Every code answers — there is no "no extended information available" case, because a code with no entry fails the build. A rendered batch of diagnostics now closes with one line naming the command and a code from that batch, rather than repeating an invitation under every error. The same table is published as `docs/diagnostics.md`, generated from it with a heading per code, and that is where an editor's diagnostic link now points: the code beside a squiggle became something you can click.
- `std.list` gains `List.at`, a safe index lookup: `List.at n xs` answers `Some` of the element at zero-based index `n`, and `None` when `n` is negative or past the end of the list. The index comes first and the list last, the same argument order as `take`, `drop`, and `contains`.
- A trailing `;` reports `L016` instead of a bare "unexpected character". The semicolon is the most common reflex a newcomer carries over from a C-family language, and it was the one syntax trap with no teaching message: the lexer said what it could not do rather than what Ridge expects. It now answers that Ridge does not use `;`, because an expression ends at the end of the line — joining the family `P037`–`P040` opened. Editors offer a quick fix that deletes the character, since nothing else it could mean is legal.
- The spec now states what a send guarantees (§7.2.2). `!` is asynchronous and carries no delivery guarantee once the program ends: a message still queued when `main` returns is discarded with the actor, and whether the handler ran at all is a race — a cheap handler usually wins, an expensive one usually loses, and the same program can do both on different days. Waiting is written down rather than inferred: because mailboxes are FIFO, any synchronous interaction with an actor is a barrier for everything sent to it earlier from the same process. `?>` is the barrier to use mid-program, `Actor.stop` the one to use at the end. Draining automatically was rejected — a runtime that refused to exit until every mailbox emptied would hang on any actor that keeps receiving, trading a lost message for a program that never ends.
- Six common syntax traps now produce dedicated, teaching diagnostics in the spirit of the `let … in` guidance (`P033`). Writing `add(1, 2)` — which parses as applying `add` to the tuple `(1, 2)` — adds a hint to the type error: Ridge calls are space-separated, `add 1 2` (it fires only when the argument hugs the callee with no space, so a deliberately passed tuple stays quiet). `xs[0]` is a hard parse error (`P037`) naming `List.at` — adjacency is the tell, so `f [0]` with a space still parses as application. A bare `{ name = "a" }` where a named record is expected adds a hint to the mismatch: record literals name their constructor, `User { name = … }`. `!true` reports `P038` and points at `Bool.not`. `match x { … }` reports `P039` — arms are laid out by indentation, not braces — replacing the two-to-three-error cascade with a single message (an inline record pattern in arm position is not misread as braces). And `for`/`while` are now reserved keywords reporting `P040`: Ridge has no loops — use `List.forEach` or write a recursive function.
- `ridge reload --node`: production hot reload. The command applies the current edits to a running node, local or remote over Erlang distribution: it reads the snapshot of the build the node runs, compiles the current source, and plans the upgrade with the same checker `ridge reload --check` runs — a rejected edit prints the per-symbol verdicts and touches nothing. An accepted edit travels as a bundle (upgrade manifest plus the compiled `.beam` blobs) through a short-lived probe node; the target node's loader validates every blob before loading anything, then suspends the affected actors, swaps the code with `code:load_binary`, migrates actor state, and resumes — no filesystem on the target node is involved. Production semantics land with it: a migration that fails for one actor is retried once and then that actor is killed so its supervisor restarts it on its init state (blue/green — nobody resumes with corrupt state, and the report names each restarted actor with the reason); the old code is purged after a quiescence window (`--purge-after <s>`, default 60, `0` disables; a new upgrade cancels and reschedules a pending purge); and the apply switches the node to the structured drop policy, so every in-flight message no migration chain covers is dropped with one JSON audit line on stderr instead of the dev rendering. Success prints the one-line summary (`reloaded 2 modules, migrated 1 actors (+0 restarted), 0 in-flight messages in 12ms; old code purges in 60s`), and `--json [path]` writes the full structured report — modules, actors suspended/migrated/restarted with reasons, in-flight messages migrated, duration, purge schedule — for CI/CD and audit. `--cookie`, `--timeout <ms>`, `--release`, and `--seed` (opt-in seeding of the node's version marker on first contact) round out the flags; a node without a marker is refused loudly, and a node that dies mid-apply surfaces a clean error, never a hang.
- `ridge run --reload`: a hot-reload dev loop. The command boots a persistent named dev node (staying alive after `main` returns), watches the sources, and on every save recompiles, diffs the new build against the snapshot of what the node runs, and — when every change is auto-reloadable — applies the upgrade inside the live node: affected actors are suspended, the recompiled modules are loaded, actor state is migrated through `code_change`, and everything resumes, reporting `reloaded N modules, migrated M actors in Tms`. Body-only edits reload with state untouched; a state field added with a default is filled in place; a pure state-field rename (same type, same position) carries the value over. Edits the checker rejects — removed handlers, retyped fields, widened capabilities, anything with a migration hole — print the same per-symbol report `ridge reload --check` produces and leave the node on its current code, with `r` + Enter as the cold-restart fallback. The dev node runs `ridge_dev_<pid>@127.0.0.1` with a generated cookie (`--cookie` overrides) and applies upgrades through short-lived probe nodes; the runtime loader requires OTP 27+.
- Versioned records and `migrate` hooks: records and actor state now carry real version identity across a hot reload. Every record shape is content-hashed to a 64-bit value the generated beams and the on-disk snapshot agree on, and each constructed record is tagged with it, so a value built by older code is recognisable anywhere it travels. A type can declare its history in source — `type User @version(2) = …` with a `do … end` section holding `migrate (old: User@1) -> User = …` hooks, one per previous shape — and an actor can declare the same for its state with a `migrate (old: Counter@1) -> Counter = …` member; the `User@1` type form is legal only in `migrate` signatures (`P036` elsewhere), and ordinals resolve against the snapshot's recorded history when `@version` is absent. Each module's beams export their migration chain: hand-written hooks first, then structural edges the compiler derives for hole-free changes (renames carry the value, removed fields drop), so successive upgrades compose — a message tagged two versions back migrates straight to the current shape. At reload, an actor whose source declares a hook migrates its state through it (the hook's fill takes precedence over the mechanical default); everything else uses the derived path. Messages are migrated lazily at receive: a stale-tagged record sitting in a mailbox across the upgrade is walked through the chain before any handler sees it, a record with no applicable edge is reported on stderr and dropped rather than delivered to a handler that would `badmatch` on it (`ridge_rt:set_migrate_report(silent)` silences the dev report; the drop still happens), and the reload line reports how many messages were migrated. `ridge reload --check` understands all of this: a change the source already covers upgrades from `needs-migration` to a `migrate-hook` verdict, and the scaffolds it prints for uncovered changes roundtrip — what `--check` prints parses and compiles. Steady-state cost is ~75 ns per message for the receive-path wrapper and a fixed ~9 words per tagged record.
- Standard-library union types can be imported and used from user code. `import std.m (T, MkT)` brings the type and its constructors into scope, so the type resolves in annotations and its constructors build and match by name — with no hand-written accessor functions in between. The first one is `std.query`'s `SortOrder` (`Asc | Desc`); a constructor of any stdlib `pub type` union now lowers the same way a user-defined type's constructor does.
- Quotation: a lambda passed where a `Quote` is expected is captured as an expression tree instead of being compiled to a closure — the same idea as C#'s `Expression<Func<>>`. A predicate like `fn u -> u.age >= 18 && u.active` is type-checked against the entity's columns and reified into a `QExpr` value the program can walk at runtime. Field accesses become column references by their SQL name (a `signupYear` field reads back as `signup_year`), boolean columns work as predicates on their own, and an unknown column (`T039`), an unsupported form (`T040`), a mismatched comparison (`T041`), or an entity that can't be determined (`T042`) are reported at compile time. This is the mechanism the query layer builds on.
- Multi-parameter type classes: a class can take more than one type parameter, e.g. `class Convert a b = convert (x: a) -> b`. Instance heads list one type per parameter (`instance Convert Celsius Fahrenheit`), coherence is keyed by the whole head tuple so instances that share a leading type but differ later coexist, and a call selects the instance from the types at every head position. A head position the caller leaves undetermined is reported as an ambiguous constraint to annotate.
- Functional dependencies record that some type parameters determine others, written after the type variables as `class Tagged q p | q -> p`. The dependency `q -> p` means `q` fixes `p`: two instances that agree on `q` but disagree on `p` are rejected (`T046`), and once `q` is known the compiler infers `p` from the matching instance. This resolves a determined position the call leaves open — a method whose result type the dependency fixes needs no annotation — and checks one the call supplies, so a determined type the dependency forbids is a compile error instead of being dispatched by the head's outer constructor alone. A dependency may list several variables on either side and a class several dependencies, comma-separated (`| a b -> c, c -> a`); a name that is not one of the class's own type variables is reported (`T045`).
- The query layer compiles a captured body to SQL. `Query.toSql` turns a quoted predicate into a parameterized statement and its bind values (`Quote f -> (Sql, List SqlValue)`): each literal becomes a `?` placeholder and its value is collected left to right, so a predicate reaches the database parameterized, never interpolated. `Query.orderSql` compiles a quoted ordering key (`fn u -> u.createdAt`) together with an `Asc`/`Desc` direction into an `ORDER BY` fragment. `Query.selectSql` compiles a quoted projection — a record of columns like `fn u -> { id = u.id, year = u.signupYear }` — into a select-list, emitting `column AS alias` when a field is renamed from its source column. A quoted body now type-checks as a projection when it returns a record and as an ordering key when it returns a single column, not only a boolean predicate.
- `std.sql` gains the monomorphic bind constructors `sqlInt`, `sqlText`, `sqlBool`, and `sqlFloat`, which build a `SqlValue` of a known base type without going through the `SqlType` class.
- A function parameter can destructure in the binder: `fn area (Point { x, y }: Point) -> Int = x + y` reads the record's fields directly, and `fn diff ((a, b): (Int, Int)) -> Int = a - b` unwraps a tuple — no `let` in the body. The pattern must be irrefutable, since the function is applied to every value of its type; a refutable one such as `fn f (Some x: Option Int)` is rejected with `T043`. The annotation is required, so an un-annotated pattern parameter still reports `P012`.
- A type class can be instanced over a function type, so a bare function satisfies a class constraint without a wrapper. `instance Run (Int -> Int)` makes any one-argument function a `Run`, and a plain `fn x -> x + 1` passed where `Run` is required dispatches to it — at a direct call or forwarded through a constrained consumer (`fn useRun (f: a) … where Run a`). Dispatch keys on the function's arity; the capability annotation is not part of the key yet, so a pure and an effectful handler of the same arity share an instance. A function whose arity has no instance reports the usual `T029`. This is the groundwork for passing bare functions where a handler is expected.
- `deriving (Row)` reads a database row back into a record. A row is a `Map Text SqlValue` keyed by column name; the derived `Row` instance's `fromRow` reads each field from its column — the same snake_cased spelling the `Table` derive uses, so `createdAt` reads `created_at` — runs the field type's `SqlType.fromSql`, and returns the assembled record or the first decoding error. Field types must have a `SqlType` instance (`Int`, `Text`, `Bool`, `Float` today); a missing column or a value whose type does not match the field yields an `Err`, and deriving `Row` on a union or on a record with an unsupported field type is rejected. This is the read half of the data layer's row mapping.
- A storage `Adapter` and an in-memory adapter — the start of the data layer's backend seam (`std.data`). `Adapter` is the class every backend implements: `appendRow` appends a row to a table and `all` reads a table back, with rows crossing as `Map Text SqlValue`, so they decode straight through `deriving (Row)`. `memAdapter` opens a process-backed in-memory store for tests and local development; repository code written against `Adapter` runs unchanged against it and, later, against a real database. Opening an adapter takes the `db` capability, and the handle it returns is the proof of access — the query methods carry no capability of their own, the same handle-as-proof model an actor uses.
- The `Adapter` seam gains `selectRows`, `get`, and `delete`. `selectRows` and `delete` take a quoted predicate written against the queried record — `selectRows conn "users" (fn (u: User) -> u.age >= 18)` — captured as a `QExpr` tree; the in-memory adapter walks it against each stored row, and a real database compiles the same tree to a `WHERE` clause. `selectRows` returns the matching rows, `delete` removes them and answers how many went, and `get` looks a single row up by an exact column match. The predicate's row type is pinned by its parameter annotation, so columns and their types are checked at compile time while the rows themselves stay untyped maps that decode through `deriving (Row)` one layer up.
- A typed repository over the storage `Adapter` — the data layer's end-user query surface (`std.repo`). A `Repo e a` binds an entity type `e` to a table on an adapter `a`; its read verbs run the adapter and decode each row back into the entity through `deriving (Row)`, so a query answers `List User` rather than a list of column maps. `repo conn "users"` builds one — the entity is pinned once by the binding's annotation (`let users: Repo User MemAdapter = ...`) and flows to every call — and the verbs compose as a pipeline: `users |> Repo.findBy (fn (u: User) -> u.age >= 18)`. `all` and `findBy` answer decoded entities, `find` and `getBy` at most one, `count`/`countBy`/`exists` an aggregate, `insertRow` appends a column map and `delete` removes the rows a predicate matches. Predicates are quoted exactly as at the adapter seam, so columns and their types are checked at compile time. The repository is adapter-agnostic: the same code runs against the in-memory adapter today and a real database later.
- The repository gains a composable query builder. `Repo.query` lifts a repository into a `Query e a`; `filter` narrows it with a quoted predicate (AND-combined with any filter already set), `orderBy Desc (fn (u: User) -> u.age)` adds an ordering key — several compose, major to minor — and `limit`/`offset` page it, each pushed into one backend query rather than applied in memory. `toList` and `first` run the query and decode the matching rows into the entity. `select` and `selectFirst` instead project into a different shape: a projection names its result record with Ridge's record-construction syntax — `users |> Repo.query |> Repo.filter (fn (u: User) -> u.age >= 18) |> Repo.select (fn (u: User) -> Summary { name = u.name, year = u.signupYear })` — which fixes the decode target and lists its columns, so the backend pushes a `SELECT name, signup_year AS year …` select-list down and only those columns cross. The shape is an ordinary `deriving (Row)` record; a projection field that is not a column of the queried entity, or a projection that does not name its shape, is rejected at compile time.
- The query builder gains two-table inner joins. `Repo.joinOn` pairs a query with a second repository on a condition written against both entities at once — `users |> Repo.query |> Repo.joinOn posts (fn (u: User) (p: Post) -> u.id == p.authorId)` — and two terminals run it. `toList` decodes each matched row pair into both entities, answering `List (User, Post)`; `select` projects columns from across both sides into a named record — `fn (u: User) (p: Post) -> Line { who = u.name, title = p.title }` — and pushes that select-list down so only the named columns cross. Both the condition and the projection are checked against both records: a column neither entity declares, a comparison between mismatched column types, or a projection that does not name its shape is rejected at compile time. The left query's filter, ordering, and page still apply, and the same code runs against the in-memory adapter and Postgres.
- The join builder gains a left outer join. `Repo.leftJoinOn` reads exactly like `joinOn` but keeps every left row: a row with no matching right row survives instead of being dropped. Its `toList` terminal answers `List (User, Option Post)`, where the right entity is `Some` for a matched row and `None` for an unmatched one — the optionality is in the type, so a result paired as a plain `(User, Post)` is rejected at compile time. On Postgres it compiles to a `LEFT JOIN`; an unmatched row is told apart from a matched row whose columns happen to be NULL by a sentinel column on the right side, so an all-NULL right entity still reads as `Some`, not `None`.
- Nullable columns: a `deriving (Row)` record may declare an `Option` field over one of the base column types (`Option Int`, `Option Text`, `Option Bool`, `Option Float`). A SQL NULL — or a column that is absent from the row — decodes to `None`, and a present value to `Some`; a `SqlType (Option a)` instance also writes `None` back as NULL through `toSql`. This is the read path for any table whose columns are nullable, and the groundwork a left-join projection needs to decode the right side's columns where the row had no match.
- The left join gains a projection terminal. `Repo.select` projects a left join into a named shape, the left-outer analogue of `select`. Its projection's right parameter is `Option`, so a column read off it is `Option` of its type — `fn (u: User) (p: Option Post) -> Line { who = u.name, title = p.title }` fixes `Line` to `{ who: Text, title: Option Text }`, and an unmatched left row projects `title` as `None`. The result record's right-derived fields must therefore be `Option`; declaring one as a plain `Text` is rejected at compile time. The backend compiles a `LEFT JOIN` with the select-list pushed down, and a NULL right column decodes straight into the shape's `Option` field, the same on the in-memory adapter and Postgres.
- A typed write path for the repository. `deriving (Row)` now also generates `toRow`, the encode half of the row codec, so a record turns into a `Map Text SqlValue` the same way `fromRow` reads one back — each field runs through `SqlType.toSql`, and an `Option` field writes `None` as SQL NULL. On top of it `Repo.insert` appends a typed entity (`users |> Repo.insert (User { id = 1, age = 18, name = "ada" })`) with no hand-built column map; `Repo.update` overwrites every column of the rows a predicate matches with a typed entity; and `Repo.updateWhere` sets only the columns named in a partial map. Both update verbs answer how many rows changed: `users |> Repo.updateWhere (Map.fromList [("age", toSql 40)]) (fn (u: User) -> u.age >= 18)`. The raw `insertRow` stays for a hand-built row. The `Adapter` seam gains the matching `updateRows` primitive — the in-memory backend merges the change map into each matching row, and Postgres compiles a parameterised `UPDATE … SET … WHERE` whose SET binds precede the predicate's, the same repository code running over both.
- Typed setters for partial updates, where `updateWhere` takes an unchecked column map. `Repo.set` names a column with a quoted accessor and pairs it with a value — `Repo.set (fn (u: User) -> u.age) 99` — and the accessor pins the column's type, so the value must match it: assigning a `Text` to an `Int` column is rejected at compile time, the same way a predicate's comparison is checked. The value is encoded through `SqlType.toSql`, so a nullable column takes an `Option` (`Repo.set (fn (u: User) -> u.nick) None` writes NULL). A list of setters drives two verbs: `Repo.setWhere` applies them over the repository with an explicit predicate — `users |> Repo.setWhere [Repo.set (fn (u: User) -> u.status) "adult"] (fn (u: User) -> u.age >= 18)` — and `Repo.applySet` is the query-builder write terminal, so the accumulated `filter` picks the rows and the setters assign their columns (`users |> Repo.query |> Repo.filter (...) |> Repo.applySet [...]`), reading the way `Where(...).ExecuteUpdate(...)` does in LINQ. Both answer how many rows changed and compile to the same `updateRows` seam as `updateWhere`, on the in-memory adapter and Postgres alike.
- The repository's projection terminals are unified into one verb. A single `Repo.select` projects a query, an inner join, or a left join into a named shape — `users |> Repo.query |> Repo.select (fn (u: User) -> Summary { name = u.name })`, `… |> Repo.joinOn posts (…) |> Repo.select (fn (u: User) (p: Post) -> Line { … })`, and the left-join form whose right parameter is `Option` — the receiver fixing the projection's arity, so a one-row projection on a join (or a two-row one on a plain query) is a compile error rather than a silent mismatch. `Repo.selectFirst` is the one-row counterpart over each receiver, answering `Option s` with a pushed-down `LIMIT 1`. Both are methods of a `Projectable q p | q -> p` class — the same functional-dependency overload that unified `filter`, so one verb serves all three receivers and the projected element type is the projection's own return. The select-list still carries only schema-checked entity columns: a projection field bound to a literal or any non-column expression is rejected, so a projection can never reach the database as raw SQL. The `Adapter` seam's own row-fetch primitive is renamed `selectRows`, freeing the user-facing `select`.
- Call arguments can continue onto deeper-indented lines when they open with `[`, `(`, or `{`, so a multi-argument call no longer has to fit on one physical line:

  ```
  users
      |> Repo.setWhere
          [ Repo.set (fn (u: User) -> u.status) "adult" ]
          (fn (u: User) -> u.age >= 18)
  ```

  An indented line that starts with one of those brackets folds onto the line above it as another argument instead of opening a fresh block. The continuation does not fire after a line that ends with a block introducer (`=`, `->`, `then`, `else`, `try`) or for a `match` arm, so block bodies and arm patterns still indent as before — only shapes that were a layout error (`P006`) before now read as a continuation.
- Scalar aggregates on the query builder. `Repo.sumOf`, `Repo.avgOf`, `Repo.minOf`, and `Repo.maxOf` fold a column the backend names with a quoted accessor over the rows a query selects — `users |> Repo.query |> Repo.filter (fn (u: User) -> u.age >= 18) |> Repo.sumOf (fn (u: User) -> u.age)` — pushed down as a `SELECT func(col) … WHERE` rather than fetched and folded in memory, like `count`. The accumulated `filter` bounds the rows, and ordering and paging pick the window the aggregate folds: `… |> Repo.orderBy Desc (fn (u: User) -> u.age) |> Repo.limit 10 |> Repo.sumOf (fn (u: User) -> u.age)` sums the ordered top-ten, the way LINQ's `Take(10).Sum()` reads. Each answers an `Option`, with `None` when no row matches — a SQL aggregate over zero rows is NULL, not zero, so reach for `Option.withDefault 0` for the LINQ-style zero. `sumOf`/`minOf`/`maxOf` keep the column's own type (`sumOf` over an `Int` column is `Option Int`, `maxOf` over a `Text` column is `Option Text`); `avgOf` is always `Option Float`, since an average is fractional even over an integer column. The `Adapter` seam gains the matching `aggregate` primitive — the in-memory backend folds the matching rows, and Postgres compiles the aggregate into the query — so the same code runs over both.
- Unique-row and universal terminals on the query builder. `Repo.single` runs a query that should identify one row and answers `Option`: `None` when none match, the decoded entity when exactly one does, and an error when more than one does. `Repo.singleOrError` is the strict form — an empty match is an error too, so it answers the bare entity or fails. Both fetch with a two-row limit, so the backend stops as soon as a second match proves the result is not unique rather than scanning the table. `Repo.every` is the universal dual of `exists`: it takes a further predicate and answers whether every row the query selects satisfies it, counting both sides on the backend (`exists` asks whether any row matches; `every` whether all do). An empty selection is `true`, the vacuous reading SQL gives a universal over no rows. All three compose after the accumulated `filter` and run the same on the in-memory adapter and Postgres.
- Grouped aggregates on the query builder. `Repo.groupBy` partitions a query by a key column and `Repo.summarize` projects each group into a named record built from the group itself: `g.key` is the group key, `g.count` the row count, and `g.sum`/`g.avg`/`g.min`/`g.max` fold a column named by an accessor — `users |> Repo.query |> Repo.groupBy (fn (u: User) -> u.dept) |> Repo.summarize (fn g -> DeptStats { dept = g.key, members = g.count, payroll = g.sum (fn (u: User) -> u.salary) })`. The aggregate types flow from the columns, so `g.sum` over an `Int` column is an `Int` and `g.avg` is a `Float`, and the named record fixes the result shape the way a `select` projection does. `Repo.having` keeps only the groups whose aggregate condition holds — a real SQL `HAVING` — written over the same vocabulary: `Repo.having (fn g -> g.count > 3)` or a threshold on a different aggregate, `Repo.having (fn g -> g.sum (fn (u: User) -> u.salary) >= 100000)`. The query's `filter` bounds the rows before they group, the groups come back ordered by the key, and the whole pipeline pushes a `SELECT … GROUP BY … HAVING …` down to the backend rather than folding in memory — the same on the in-memory adapter and Postgres. The group vocabulary is captured at compile time, so an unknown column in an aggregate or a projection field that is not a group aggregate is rejected with the rest of the quote checks.
- A `distinct` modifier on the query builder. `Repo.distinct` drops duplicate rows from a query's result — a `SELECT DISTINCT` — composing between `filter`/`orderBy` and a terminal like the other builder verbs: `users |> Repo.query |> Repo.distinct |> Repo.toList`. Over a whole-row `toList` it removes exact repeats; over a `select` projection it dedups the projected columns, so `users |> Repo.query |> Repo.distinct |> Repo.select (fn (u: User) -> Dept { dept = u.dept })` returns each distinct value once. The backend pushes it down — `SELECT DISTINCT` on Postgres, a dedup over the matching rows on the in-memory store — so the same code runs over both.
- Set operations on the query builder. `Repo.union`, `Repo.unionAll`, `Repo.intersect`, and `Repo.except` combine two queries over the same entity into one — `active |> Repo.union admins` — and the result is itself a `Query`, so it keeps composing through the ordinary verbs: `active |> Repo.union admins |> Repo.orderBy Asc (fn (u: User) -> u.name) |> Repo.limit 10 |> Repo.toList`. A combined query can be combined again (`(a ∪ b) ∪ c` nests), and a further `filter`/`orderBy`/`limit`/`offset`/`distinct` applies on top of the combination. `union` removes the rows the two branches share, `unionAll` keeps them, `intersect` keeps the rows in both, and `except` keeps the left rows not in the right (order matters there — the piped-in query is the left side). The combination runs in the backend, dispatched by the adapter the query carries: Postgres compiles a real `UNION`/`UNION ALL`/`INTERSECT`/`EXCEPT` (each branch a subquery, with the bind placeholders threaded across the whole statement so they never collide), and the in-memory store evaluates the plan over its rows. Both branches range over the same entity and adapter, so the column shapes line up — the type each branch carries pins the entity it decodes back to and which backend runs the combination.
- Type-class methods can be called module-qualified, the same as a plain function. A method declared in a module is reachable through that module's alias — `Sql.toSql x` for a standard-library class, or `L.describe x` for a class you declared in another module imported `as L` — and dispatches on the receiver exactly as the bare call does. The qualified form is scoped to the class's declaring module: a name that is also an ordinary function elsewhere (`Int.toText`, `List.filter`) still calls that module's own function, and a method reached through a module that does not declare its class stays unresolved (`R012`). Before this, a qualified class method either failed to resolve or compiled to a missing symbol, so an unqualified import was the only way to reach one.
- One `filter` for both a query and a join. `Repo.filter` now narrows a `Join` or `LeftJoin` as well as a `Query`: on a query it takes a one-row predicate over the entity, on a join a two-row predicate over both — `users |> Repo.query |> Repo.joinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.filter (fn (u: User) (p: Post) -> p.published) |> Repo.toList`. The predicate's arity follows the receiver through a functional dependency, so writing a two-row predicate on a query, or a one-row predicate on a join, is a compile-time arity error rather than a silent mismatch. On a join the predicate compiles to a post-join `WHERE`: a condition over a right column drops the rows that do not match, and on a left join it drops the unmatched left rows too — their right side is NULL, so the predicate reads false — narrowing the outer join to its matches the way a `WHERE` after a `LEFT JOIN` does in SQL. A predicate that touches only the left row keeps the unmatched rows. The same `filter` runs over the in-memory adapter and Postgres.
- One `orderBy` for both a query and a join. `Repo.orderBy` now orders a `Join` or `LeftJoin` as well as a `Query`: on a query the key is a one-row column over the entity, on a join a two-row key over both — and a join's key may name a column from *either* side, so `users |> Repo.query |> Repo.joinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.orderBy Desc (fn (u: User) (p: Post) -> p.title) |> Repo.toList` sorts the pairs by the right table's column. The key's arity follows the receiver through a functional dependency, so a two-row key on a query, or a one-row key on a join, is a compile-time arity error. Keys compose major-to-minor in the order added, and the ordering a query accumulated before a `joinOn` carries into the join as left-side keys. Like `filter` and `select`, `orderBy` is the method of an `Orderable q p | q -> p` class — the receiver fixing the key's shape — and the key stays column-only: a computed expression or an unknown column is rejected, so nothing but a schema-checked column reaches the generated `ORDER BY`. The backend qualifies each key to the left or right table accordingly, the same on the in-memory adapter and Postgres.
- One set of scalar aggregates for both a query and a join. `Repo.sumOf`, `Repo.avgOf`, `Repo.minOf`, and `Repo.maxOf` now fold a column over a `Join` or `LeftJoin` as well as a `Query`: on a query the accessor is a one-row column over the entity, on a join a two-row one over both — and a join's accessor may fold a column from *either* side, so `users |> Repo.query |> Repo.joinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.sumOf (fn (u: User) (p: Post) -> p.views)` sums the right table's column. The accessor's arity follows the receiver through a functional dependency, so a two-row accessor on a query, or a one-row one on a join, is a compile-time arity error. Like `filter`, `select`, and `orderBy`, the aggregates are methods of an `Aggregable q p | q -> p` class — the receiver fixing the accessor's shape, the result keeping the column's own type (`avgOf` is always `Option Float`), and `None` over an empty fold. On a left join the accessor reads the right side as the plain entity rather than `Option` the way `select`/`orderBy` do, because an aggregate folds values instead of producing one per row: a right-column fold skips the unmatched left rows (their right column is NULL, which a SQL aggregate ignores) while a left-column fold still counts them. The accessor stays column-only — a computed expression or an unknown column is rejected — and the `Adapter` seam gains the matching `aggregateJoin`/`aggregateLeftJoin` primitives, the backend qualifying the column to the left or right table, the same on the in-memory adapter and Postgres.
- One pair of decode terminals for both a query and a join. `Repo.toList` and `Repo.first` now run a `Join` or `LeftJoin` as well as a `Query`, decoding each into the receiver's own row shape: a query into its entity, an inner join into a pair `(User, Post)`, a left join into a pair whose right side is optional `(User, Option Post)` — `users |> Repo.query |> Repo.joinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.toList`. They replace the per-receiver `toPairs`/`toLeftPairs`, and give a join the `first` terminal it lacked: the first decoded row pair, fetched with a pushed-down `LIMIT 1`, or `None` when none match. Unlike the other unified verbs, the terminals take no quoted argument — the row follows from the receiver alone, named through a `Rows q` projection that reduces to the entity for a query, a pair for an inner join, and an optional-right pair for a left join — so a query whose entity the call site never pins still resolves it from the declared result type. A left join keeps every left row, its right side decoding to `None` where the row matched none. The same terminals run over the in-memory adapter and Postgres.
- One set of paging and `distinct` modifiers for both a query and a join. `Repo.limit`, `Repo.offset`, and `Repo.distinct` now bound and de-duplicate a `Join` or `LeftJoin` as well as a `Query` — `users |> Repo.query |> Repo.joinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.orderBy Asc (fn (u: User) (p: Post) -> p.id) |> Repo.limit 10 |> Repo.toList` keeps the first ten joined pairs, and `Repo.distinct` over a join drops duplicate rows (a `SELECT DISTINCT` over both sides, or over the projected columns when a `select` follows). Unlike the other unified verbs they take no quoted argument and do not change the row shape, so they are the methods of a single-parameter `Pageable q` class with no functional dependency: a query, an inner join, and a left join all carry the same three. A join keeps its own page and distinct, lifted from the left query at `joinOn`, so paging or de-duplicating the join bounds the joined result rather than the left table alone. The `Adapter` seam's join primitives gain the `distinct` flag they lacked — the in-memory backend dedups the joined rows, Postgres compiles `SELECT DISTINCT … JOIN …` — so the same code runs over both.
- One set of count-and-test terminals for both a query and a join. `Repo.count`, `Repo.exists`, and `Repo.every` now run a `Join` or `LeftJoin` as well as a `Query`: `count` answers how many rows the receiver selects, `exists` whether it selects any, and `every` whether all of them satisfy a further predicate — `users |> Repo.query |> Repo.joinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.count` counts the joined pairs, and `… |> Repo.every (fn (u: User) (p: Post) -> p.published)` tests them. Each is counted by the backend — a pushed-down `COUNT(*)` over the join, or a one-row probe for `exists` — never fetched and measured. `count` and `exists` take no quoted argument, so they are the methods of a single-parameter `Countable q` class like the decode terminals; `every` takes a predicate whose arity follows the receiver through a functional dependency, so it is the method of an `Every q p | q -> p` class — a one-row predicate over a query, a two-row one over a join, and a wrong-arity predicate a compile-time error. They run off the query builder rather than the bare repository, so a whole-table count reads `users |> Repo.query |> Repo.count` and a count over a predicate folds a `filter` in first — the form the removed `Repo.countBy` spelled directly. Like the scalar aggregates, they answer over the window ordering and paging select — a paged `count` counts the page and a paged `every` tests only the page — and a query's set-operation plan is honoured the way the decode terminals honour it. On a left join `every` reads its right side as the plain entity (as `filter` does), so a predicate over a right column fails the unmatched rows under SQL's three-valued reading. The `Adapter` seam gains the matching `countJoin`/`countLeftJoin` primitives — the in-memory backend counts the joined rows, Postgres compiles `SELECT COUNT(*) FROM l JOIN r` (a `LEFT JOIN` for the left-outer count) — so the same code runs over both. LINQ's `Count`/`Any`/`All` over a join.
- Grouped aggregates over a join. `Repo.groupBy`, `Repo.having`, and `Repo.summarize` now partition and summarise an inner or left join as well as a plain query — `users |> Repo.query |> Repo.joinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.groupBy (fn (u: User) (p: Post) -> p.category) |> Repo.summarize (fn g -> CatStats { cat = g.key, posts = g.count, score = g.sum (fn (u: User) (p: Post) -> p.score) })`. The key is a two-row accessor naming a column from either side, and a `summarize` aggregate folds a column from either side too: `g.sum (fn (u: User) (p: Post) -> p.score)` sums the right table, `g.sum (fn (u: User) -> u.age)` the left. `Repo.having` reads the same group vocabulary over the join, including a threshold on a side-qualified aggregate (`Repo.having (fn g -> g.sum (fn (u: User) (p: Post) -> p.score) >= 100)`). All three are the methods of two new classes — `groupBy` of a `Groupable q p | q -> p` overload whose dependency fixes the key's arity per receiver, and the per-source backend dispatch of a `Summarizable q` class behind `summarize` — so one set of verbs serves a query, an inner join, and a left join, and the grouped builder they thread, `Grouped q p`, carries the source through `having` into `summarize` without a per-receiver type. The pipeline pushes a `SELECT … FROM l JOIN r … GROUP BY … HAVING … ORDER BY …` down to the backend, each column qualified to its table, the same on the in-memory adapter and Postgres; a left join keeps every left row, an unmatched one grouping with its right columns read as NULL. A left-join aggregate reads its right side as the plain entity, as the join scalar aggregates do — it folds values rather than producing one per row. LINQ's `GroupBy`/`Having` over a join.
- Database transactions on the repository. `Repo.transaction conn body` runs a body on the connection inside a transaction: it commits and returns the body's value when the body answers `Ok`, and rolls back — leaving the store as it was — when the body answers `Err`, so a multi-step write is all-or-nothing. The body receives the same connection, so the repositories built on it run within the transaction; a body that inserts two rows lands both, or if the second fails, neither. A `transaction` nested inside another opens a savepoint: an inner `Err` rolls back only the inner work and the outer transaction carries on, so a failable sub-step can be attempted without abandoning the whole transaction. The body may carry any effect — its capability row flows out to the call the way a list higher-order function's callback does — and the result is the body's own success type. The `Adapter` seam gains the `begin`/`commit`/`rollback` primitives behind it: the in-memory backend snapshots the affected tables and restores them on rollback, and Postgres issues `BEGIN`/`COMMIT`/`ROLLBACK` (or `SAVEPOINT`/`RELEASE SAVEPOINT`/`ROLLBACK TO SAVEPOINT` when nested) on a single connection pinned for the transaction's span, so every operation between `begin` and the matching terminal runs on it. The same code runs over the in-memory adapter and Postgres.
- Schema migrations through a typed DSL (`std.migrate`). A migration is a named, ordered batch of schema changes; `Migrate.run conn schema` applies the ones not yet recorded — each inside its own transaction, so a migration's changes and the record of it landing commit together — and answers the names it applied. Running the same list again applies nothing, so a project keeps its schema as one growing list and runs it on startup. Schema changes are built without raw SQL: `createTable` with a list of columns, `dropTable`, `addColumn`/`dropColumn`, and `createIndex`/`uniqueIndex`. A column is declared by its base type — `intCol`, `textCol`, `boolCol`, `floatCol` — and refined with the pipe-friendly steps `nullable`, `primaryKey`, and `unique` (`textCol "email" |> unique`). On Postgres the DSL compiles to `CREATE TABLE` / `ALTER TABLE` / `CREATE INDEX`, and the applied migrations are tracked in a `_ridge_migrations` table the runner creates on first use; on the in-memory adapter a create materialises a table and a drop forgets one, with the column and index changes a no-op on the schemaless store. The `Adapter` seam gains the schema and migration-tracking primitives behind the runner, so the same migrations run over either backend.
- A raw-SQL escape hatch over the storage adapter (`std.raw`). When the query builder cannot express a statement — a recursive CTE, a window function, a vendor extension — `Raw.query conn sql params` runs it and decodes each row into an entity through `deriving (Row)`, `Raw.queryFirst` keeps the first, and `Raw.exec` runs a row-less statement (INSERT/UPDATE/DELETE/DDL) for its affected row count. A statement is always parameterised: its values ride positional placeholders (`$1`, `$2`, … on Postgres) as bound `SqlValue`s built with `sqlInt`/`sqlText`/`sqlBool`/`sqlFloat`, so a value is never spliced into the SQL text and the statement is injection-safe. The selected columns decode by name, so a computed column is aliased to a field (`SELECT count(*) AS n` decoded into `{ n: Int }`) — the way to read a scalar back. Raw SQL is a SQL backend's surface: it runs on Postgres, and the in-memory adapter, which has no SQL engine, answers a clear error instead, so a function that mixes builder queries with a raw one stays adapter-agnostic and only the raw call fails on the memory store. The `Adapter` seam gains the `rawQuery`/`rawExec` primitives behind it.
- A cross join on the query builder. `Repo.crossJoin` pairs a query with a second repository and no condition — the cartesian product, every left row matched with every right row: `users |> Repo.query |> Repo.crossJoin colors |> Repo.toList`. A cross join is an inner join whose condition is always true, so it reuses the same `Join e f a` and inherits the whole join vocabulary — `filter`, `select`, `orderBy`, the scalar aggregates, paging, `count`/`exists`/`every`, and `groupBy`/`summarize` all compose on it the way they do after `joinOn`, and `toList` decodes each pair into `(User, Color)`. A later `filter` over both rows turns the product into a non-equi join — `… |> Repo.crossJoin colors |> Repo.filter (fn (u: User) (c: Color) -> u.score > c.threshold)` — the pairing left to the predicate rather than an `ON`. Unlike `joinOn`, it takes no condition argument. The same code runs over the in-memory adapter and Postgres.
- The join builder gains a right outer join, the mirror of `leftJoinOn`. `Repo.rightJoinOn` keeps every *right* row: a row from the right repository with no matching left row survives instead of being dropped, and its `toList` answers `List (Option User, Post)` — the optionality moves to the left, `Some` for a matched row and `None` for an unmatched one — so a result paired as a plain `(User, Post)` is rejected at compile time. The whole join vocabulary composes on it the way it does after `leftJoinOn`: `filter`, `select` (whose left parameter is now the `Option`, `fn (u: Option User) (p: Post) -> …`), `orderBy`, the scalar aggregates, paging, `count`/`exists`/`every`, and `groupBy`/`summarize`. The left query's own filter folds into the join match rather than the post-join `WHERE`, so narrowing the left side restricts which rows pair without ever dropping a right row — `users |> Repo.query |> Repo.filter (fn (u: User) -> u.active) |> Repo.rightJoinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.toList` returns every post, pairing each with its author only when that author is active and `None` otherwise. On Postgres it compiles to a `RIGHT JOIN`; an unmatched right row is told apart from a matched row whose left columns happen to be NULL by a sentinel column on the left side, so an all-NULL left entity still reads as `Some`. The same code runs over the in-memory adapter and Postgres.
- The join builder gains a full outer join, the union of the left and right joins. `Repo.fullJoinOn` keeps every row of *both* tables — a left row with no match and a right row with no match both survive — so its `toList` answers `List (Option User, Option Post)`, each side `Some` where the row matched and `None` where it did not, and a result paired as a plain `(User, Post)` (or with only one side optional) is rejected at compile time. The whole join vocabulary composes on it: `filter`, `select` (whose *both* parameters are now `Option`, `fn (u: Option User) (p: Option Post) -> …`), `orderBy`, the scalar aggregates, paging, `count`/`exists`/`every`, and `groupBy`/`summarize`. Unlike a right join — where the left query's filter folds into the join match because unmatched left rows are dropped anyway — a full join keeps unmatched left rows, so the filter restricts which left rows enter the join rather than folding into the `ON`: a left row it rejects never appears, not even unmatched. `users |> Repo.query |> Repo.filter (fn (u: User) -> u.active) |> Repo.fullJoinOn posts (fn (u: User) (p: Post) -> u.id == p.author) |> Repo.toList` returns every active user and every post — matched where an active author owns a post, the active authors with no post paired with `None`, and the posts whose author is inactive or missing paired with `None`. On Postgres it compiles to a `FULL JOIN` with a sentinel column on each side, so an all-NULL entity on either side is still told apart from a real one; both sides become derived subqueries, so the decoder splits the joined row at the left sentinel marker rather than by column attribute number. The same code runs over the in-memory adapter and Postgres.
- Scoped connection lifecycle. `Repo.withConnection conn body` runs the body with a connection and then releases it on *every* path — whether the body answers `Ok` or `Err` — returning the body's own result. A Postgres connection's pool is shut and its sockets closed; an in-memory adapter's store is forgotten. Because the release is guaranteed, a connection is never leaked even when the body returns early or fails, the way a bare open-and-use pair leaks it on the error path — the same bracket pattern `Repo.transaction` follows for `begin`/`commit`/`rollback`. The release is best-effort teardown: a failure to release does not turn a successful body into an error. For a long-running application the pattern is unchanged — `connect` once and reuse the handle, whose pool reuses connections across operations — and `withConnection` is for the bounded scopes (a task, a request) that should hand their connection back when they finish. It runs over the in-memory adapter and Postgres.
- The language server now serves pull diagnostics (LSP 3.17) for editors that ask for them. An editor that advertises both the pull request and a refresh switches to the pull model: it fetches diagnostics for a document, or for the whole workspace, when it wants them, and the server asks it to re-fetch after each recompile rather than pushing. Editors that advertise only one half, or neither, keep the push model exactly as before. The endpoint is advertised only to editors that support it, which also settles an old rough edge where advertising it without serving it made some clients report a "method not found" error on every file they opened.
- A union variant can carry an inline record, and it now constructs and pattern-matches like one. `type Event = Login { userId: Int, at: Timestamp } | Logout { userId: Int, reason: Text }` declares two record-carrying variants; `Login { userId = 1, at = now }` builds one and `match e { Login { userId, .. } -> … }` reads it back — the fields are checked against that variant's own record and bound by name in any order, with a rest pattern (`..`) ignoring the ones you don't name. The match is a real case split: exhaustiveness treats each record variant as its own case, so a match that omits one is still reported (`T016`, its witness shown record-style as `Logout { userId = _, reason = _ }`) and a sibling arm after a record-variant arm is never wrongly flagged redundant. A mistyped or missing field is reported at the construction and the pattern the same way it is for a record type, and generic unions carry record variants too (`type Box a = | Wrap { val: a }`). `deriving` understands the variant as well: `ToText` renders it `Login { userId = 1, at = 2 }`, `Eq` and `Ord` compare its fields in declared order, and `Encode`/`Decode` round-trip it through JSON, all in one union alongside positional and nullary variants. Such a variant previously parsed and declared but could not be constructed or matched.
- Typed supervision for actors (`std.actor`). A `child Counter (args…)` expression builds a typed `ChildSpec a` — a pure value describing how to start one actor, so building a spec starts nothing — and `Actor.supervise strategy intensity periodMs specs` starts an OTP supervisor over a list of them. The strategy picks who is restarted when a child dies (`OneForOne`, `OneForAll`, `RestForOne`); the intensity and period bound the restart rate, past which the supervisor gives up and terminates. A handle from `Actor.startChild` keys on the child's registration id rather than its process id, so sends, asks, and `Actor.mailboxSize` follow the replacement process after a restart — only the state resets. Children can also come and go at runtime: `startChild` starts a spec on a running supervisor, `stopChild` terminates and unregisters an id, `whichChildren` lists the `(id, alive)` pairs, and `childId`/`childRestart` adjust a spec before it starts. `Actor.tryAsk handle msg timeoutMs` is the `Result`-returning ask — `Ok reply`, `Err Noproc`, or `Err Timeout` — while `?>` on a target that no longer exists fails fast with the structured `ridge_ask_noproc` reason; a dead supervisor fails just as loudly (`ridge_sup_noproc` from `whichChildren`, `Err "supervisor_not_running"` from `startChild`/`stopChild`). Supervisors start unlinked, extending the rule that `spawn` shares no fate: a supervisor ties its children's lifetimes, not its starter's. See spec §7.5.
- The language server covers the supervision surface. `child` is offered in completion and highlighted as a keyword in the editor grammars — while staying a legal variable name, since it is a contextual keyword: renaming a binding to `child` is allowed, unlike the reserved `spawn`. Go-to-definition on the actor name in `child Counter` lands on the actor's declaration, and `Actor.tryAsk` — a function the compiler types specially, with no declaration of its own in the stdlib sources — answers hover, go-to-definition, signature help, and completion documentation instead of coming back empty.
- The capability quick-fix covers the whole capability surface. Beyond an unannotated top-level function, the "add the missing capabilities" action now works on a partially annotated function (only the missing ones are inserted, so `fn io partial` becomes `fn io fs partial`), on an `on` handler, and on an `init` block (inserted after the `init` keyword). A `T018` call-site error offers the same widening on the caller, whether it is a function, a handler, or an `init`. An inner function whose annotation exceeds its enclosing function's set gets the fix in the honest direction — widening the *enclosing* signature. And a `T019` leak — an `init` declaring a capability no handler on the actor declares — offers to remove the excess from the `init`, saying so in the action's title. When a `T014` and its `T018` would produce the same edit, the action is offered once.
- Actor `terminate` callbacks. An actor may declare one `terminate [caps] (reason: ExitReason) = body` member — cleanup code that runs when the actor's process stops: on an ordered stop from a supervisor (`stopChild`, a sibling shutdown under `one_for_all`, intensity exhaustion) with `Shutdown`, and on a handler crash with `Crashed`, which carries the OTP exit reason rendered as text. The body may read state fields (flushing them is the canonical use) and is capability-checked like `init`: its declared set must stay within the union of the actor's handler caps, and `spawn` callers never inherit it. The callback does not run when `init` itself crashes, nor on a `brutal_kill` — those stops give no callback a chance, and the spec says so. `terminate` is a contextual word, so it stays a legal identifier elsewhere; a second `terminate` member (or a second `init`/`mailbox` — the at-most-one rule was documented but never enforced) is now a resolve error (`R029`). See spec §3.9 and §7.5.
- The language server covers the `terminate` member. It is offered in completion and highlighted in the editor grammars while staying a legal variable name (contextual, like `child`), and the capability quick-fixes anchor after the member keyword: a missing capability in the body offers to widen the callback's prefix (`T014`/`T018`), and a capability no handler on the actor declares offers to remove it (`T019`). The `init` arm of the `T018` fix also stops anchoring at the call site — the edit now lands after the member keyword where it belongs.
- User-level process monitors (`std.actor`). `Actor.monitor handle` returns an opaque `Monitor` reference — a new compiler-known builtin, since a BEAM `reference()` has no Ridge type to alias — and a process's death is then observable in two ways: `Actor.await m timeoutMs` blocks sequential code (`main`, `init`, plain functions) up to the timeout and answers `Option ExitReason` (carrying `time`, like `Time.sleep`; `None` on timeout, with the monitor removed), while an actor that must react asynchronously declares an `onDown (m: Monitor) (reason: ExitReason) = body` member, which receives the DOWN as a message and may read and mutate state like a cast handler. `ExitReason` gains a third variant `NotRunning` for monitoring an already-dead process — it never reaches `terminate`, but matches over the union must now cover it. `Actor.unmonitor m` cancels a monitor. Monitors observe pids, not logical handles: a supervised child that crashes and is restarted fires DOWN for the old pid, so observing the new incarnation takes a fresh `monitor` call. A DOWN delivered to an actor without `onDown` is discarded, and a delivered `Monitor` correlates against stored ones with `==`. See spec §3.9 and §7.5.
- The language server covers the `onDown` member and the monitor surface. `onDown` is offered in completion and highlighted in the editor grammars while staying a legal variable name (contextual, like `terminate`), the capability quick-fixes anchor after its keyword the same way, and hover over `Actor.monitor`/`unmonitor`/`await` shows the stdlib declaration and its doc.
- Explicit transaction isolation levels. `Repo.transactionWith level conn body` runs a transaction at one of the four levels of `std.data`'s `IsolationLevel` — `ReadUncommitted`, `ReadCommitted`, `RepeatableRead`, `Serializable` — while `Repo.transaction` keeps opening at the connection's default: `PoolConfig.defaultIsolation` for Postgres (`ReadCommitted` out of the box, changed with `withDefaultIsolation`) and `SqliteConfig.defaultIsolation` for SQLite (`Serializable`, changed with `withSqliteDefaultIsolation`). Postgres honors all four levels natively — its `ReadUncommitted` reads as `ReadCommitted`, as PostgreSQL documents; SQLite is serializable by default and distinguishes only `ReadUncommitted`, a `PRAGMA read_uncommitted` span for the outer transaction restored on close, so `ReadCommitted` and `RepeatableRead` degrade to `Serializable`; and the in-memory adapter is trivially serializable and accepts any level. A `transactionWith` nested inside an open transaction must name the level already in force: the same level opens a savepoint, a different one fails with an `Err` whose `dbErrorKind` is `Unsupported` (code `db.tx.isolation_mismatch`), and a plain nested `Repo.transaction` demands no level and always opens a savepoint. The two configuration records carry the new field themselves: `PoolConfig` and `SqliteConfig` each gained a required `defaultIsolation` field, so code that builds either record literally must add it — the `defaultPool ()`, `sqliteFile`, and `sqliteMemory` constructors are unchanged in use.
- Transient-retry combinators for the data layer: `Repo.retryWhen` (generic loop; the attempt sees its 1-based attempt number), `Repo.retryTransient` (specialized to the storage seam), and `Repo.transactionWithRetry` (re-runs a whole transaction on a transient failure). All three declare the `time` and `random` capabilities — the backoff pause and its jitter.
- `dbErrorIsTransient` classifies the transient contention codes (Postgres `40001`/`40P01`, SQLite busy/locked); transport faults are never retried, since the driver cannot know whether a write committed.
- `RetryPolicy` (`maxAttempts`/`baseBackoffMs`/`maxBackoffMs`) with `defaultRetryPolicy` and `withRetryMaxAttempts`/`withRetryBaseBackoffMs`/`withRetryMaxBackoffMs`; exponential backoff with full jitter.
- Per-pool retry defaults: `commandRetry` on `PoolConfig` and `SqliteConfig` (with `withCommandRetry`/`withSqliteCommandRetry`), used by `Repo.transactionWithRetry` when called with `None`; `Adapter` gains a `retryPolicy` method.
- A normal stop for any actor: `Actor.stop handle` asks the process to stop (cap-free — the handle is the proof of access), running its `terminate` callback and notifying its monitors with the new `ExitReason.Normal` variant, and answering once the process is down. Stopping an already-dead handle is a no-op. Until now the only normal-stop surface was `Actor.stopChild` on a supervised child. See spec §3.9 and §7.5.
- The type checker validates the `terminate` and `onDown` signatures: `terminate` takes at most one parameter of type `ExitReason`, and `onDown` takes exactly a `Monitor` and an `ExitReason` in that order — a violation is a `T048` at check time, where a wrong `terminate` arity previously surfaced as a late codegen error and a wrong parameter type was never diagnosed at all.
- The result-returning send: `Actor.send handle message` takes the same handler-label message as `!` (checked against the target actor's handlers, `T015`/`T003` as usual) but answers `Result Unit SendError` — a full bounded `error`-policy mailbox yields `Err MailboxFull` instead of raising an exit signal in the caller, so backpressure is recoverable. A full drop-policy mailbox and a dead target answer `Ok ()`, exactly as with `!`. Cap-free; `SendError = MailboxFull` is a new `std.actor` union. This ships the surface deferred in 0.2.7 in the form that fits today's message model — handler labels, not first-class message values. See spec §7.2.1.
- `std.crypto` gains digests and base64: `sha256` and `hmacSha256` (pure — the same input always hashes the same; render with `Bytes.toHex`), and `base64Encode`/`base64Decode` (RFC 4648; decode returns `Result Bytes Error`, so malformed input is an `Err`, not a crash).
- `List.sum` totals a `List Int`, and `Map.filterMap` maps and filters a map in one pass — `Map.filterMap (fn k v -> …) m` keeps each `Some` under its key and drops the `None`s.
- The language server completes pipelines by type. After `x |> ` the offers are bare-imported functions whose last parameter accepts `x`'s type (the pipe feeds the last argument), and after `x |> Alias.` the alias's exports are filtered the same way — so `xs |> List.` offers `List.map` and `List.length` but not `List.range`. Matching is by head constructor; class-method verbs and functions whose last parameter is a type variable are not offered.

### Changed

- **Breaking:** three ranges of diagnostic codes move so that no code means two things. `L001`–`L010` belonged to the lexer and to the lowering phase at once; `P001`, `P002`, `P005`, `P006` and `P009` to the parser and to package resolution; `T001`, `T002` and `T004` to the type checker and to the `@ffi` validator. Several are codes people see constantly — `T001` is the plain type mismatch, `P001` is "expected X, found Y", and `P009` is what the install scripts print when they cannot read a git version string. The phase that keeps a letter is the one the letter is named for: the lexer keeps `L001`–`L016`, the parser `P001`–`P040`, the type checker `T001`–`T054`. Lowering moves to `L101`–`L110`, package resolution's first block to `P201`–`P210` (its `P101`–`P104` stay put), and FFI validation to `T101`–`T103` — the same hundreds-block convention already used for `E101` and `E102`. A code is the one stable handle anyone has on an error, for a search box, a changelog entry or a CI filter, and it cannot do that job while it names two unrelated things. Renumbering is only free before 1.0.
- `P029` is retired. The type checker declared it inside the parser's range for a restriction that no longer exists: `fn wrap (x: a) -> { value: a } = { value = x }` compiles today, `(wrap 5).value` reads back as `Int`, and reading it as `Text` is an ordinary `T001`. The variant had no construction site anywhere, so nothing could have printed it in the first place.

- **Breaking:** `std.fs` now returns `Result _ Error` (was `Result _ Text`) on every fallible operation — `readFile`, `writeFile`, `append`, `lines`, and `readDir` — conforming to the error-channel convention every other operational module already follows. The `Error`'s `code` is the POSIX reason (`"enoent"`, `"eacces"`, …) and `message` its human-readable form; code that matched on the error text needs to read the record instead. The module also gains `mkdir`, `remove`, and `removeDir` (single-level directory create, file delete, empty-directory delete).
- **Breaking:** the OTP `normal` exit reason now maps to a new `ExitReason.Normal` variant instead of `Shutdown`, so a stop that is neither a crash nor an ordered shutdown reads as what it is. `ExitReason` is now `Normal | NotRunning | Shutdown | Crashed Text`; matches over the union must cover the new variant.
- **Breaking:** the data layer reports failures as a typed `DbError` instead of the raw builtin `Error`. Every database call — the `Adapter` methods, all of `std.repo`/`std.raw`/`std.migrate`, `connect`/`connectWith`/`connectSqlite` — now returns `Result … DbError`. A `DbError` carries the failure's `kind: DbErrorKind` in the type, so a caller matches it directly (`match e.kind / UniqueViolation -> …`) instead of sorting a code post-hoc; the backend's own `code` and `message` are still there for a log line, and `constraint`/`table`/`column` name what a constraint or not-null violation refers to (empty otherwise). Migration: `Error` annotations around data calls become `DbError`; `dbErrorKind`/`dbErrorIsTransient`/`dbErrorConstraint`/`dbErrorColumn`/`dbErrorTable` now take a `DbError` and simply read its fields; `Repo.retryWhen` stays generic in the error type. The builtin `Error` remains the channel for io/fs/time/proc and the codec layer (`fromRow`/`fromSql`).
- **Breaking:** `PoolConfig` and `SqliteConfig` gain a required `commandRetry: RetryPolicy` field — record literals must name it (or pipe `defaultPool ()`/`sqliteFile …` through the `with*` setters).
- **Breaking:** the `Adapter` class gains a `retryPolicy` method; hand-written instances must implement it (`defaultRetryPolicy ()` is the sensible answer for backends without per-handle policies).
- The safe-SQL text wrapper `Sql` — with its `sql` factory and `sqlValue` accessor — moved from `std.net.http` to `std.sql`, where it sits next to `SqlValue` and the `SqlType` codec. `std.net.http` keeps the HTML and cookie hardening helpers. Import `Sql`/`sql` from `std.sql` going forward.
- The language server now tailors each response to what the editor says it can render, rather than always sending the richest form. Hover and completion documentation fall back to plain text for a client that advertises only plain text; signature-help parameters are sent as label substrings when the client doesn't support label offsets; the document outline is flattened to a flat symbol list for a client that can't show a nested tree; and a quick-fix is delivered as a command the editor runs through `workspace/executeCommand` when it can't accept an inline code-action edit. Mainstream editors advertise all of these and see no change — the fallbacks are for the clients that don't, which previously received responses they couldn't display.
- Aggregates and the count-and-test terminals now answer over the paged window instead of ignoring `limit`/`offset`. Before, `users |> Repo.query |> Repo.orderBy Desc (fn (u: User) -> u.age) |> Repo.limit 10 |> Repo.sumOf (fn (u: User) -> u.age)` folded every matching row while `toList` on the same pipeline returned ten — a split reading. Now `sumOf`/`avgOf`/`minOf`/`maxOf` fold the ordered top-n window, and `count`/`exists`/`every` answer over the same page — a paged `count` counts the page, a paged `every` tests only the page — matching LINQ's `Take(n).Sum()`/`Count()`/`Any()`/`All()`. A query with no `limit`/`offset` compiles to the same SQL as before.

### Fixed

- A warning no longer fails the build. Whether to stop was decided by whether the diagnostic list was empty, so a warning exited 1 exactly as an error did — and the same test appeared in nine places across the CLI. `check`, `build` and `test` did their work first and reported failure afterwards, so the artefacts existed and the tests had run; only the exit code disagreed. `run --observer`, `reload` and `migrate` stopped the same way, and in the REPL it cost the reader the answer they had typed: a line that merely deserved a remark was treated as one that had failed to compile, and never evaluated. Collapsing the two severities is what makes adding a lint a breaking change for every project that trips it, and the spec already leans on warnings for advisory cases such as `discarded_result`. Both the type-check pipeline and the LSP had this right — each filters on error severity, and an editor has always drawn a warning as a warning; the CLI's last gate was the one place that disagreed. Warnings are now rendered and counted instead of fatal, with the count in the summary line (`Type-check passed with 1 warning.`), and `--deny-warnings` on `check`, `build` or `test` is how a project that wants none of them asks.

- A build directory holding an incomplete standard library is repaired instead of reused. Whether the emitted stdlib could be reused was decided by whether `std.list.beam` existed — one file standing in for the whole set — so any other module could be absent and nothing put it back: `check` passed, `build` reported success, and the program died at run time on a stdlib function that was simply not there, `'std.text':split/2` undefined, with nothing in the message pointing at the build directory. The only way out was knowing to delete `target/` by hand. Three things reach that state: an interrupted build leaves a partial set, and nothing locks the build directory, so two invocations against one project write into the same `beam/`; a compiler whose standard library gained a module never delivered it to a directory that already carried the sentinel; and the per-module check was a bare existence test, so a module that was present but stale — what rebuilding the compiler over edited stdlib sources leaves behind — was kept indefinitely. Reuse now requires a manifest written by the emit pass itself, written by the same compiler version, naming modules that are all present and none older than the compiler binary; anything short of that falls through to the emit pass, which is per-module and recompiles only what is out of date.

- The `entry` key names the module a program starts from, and is now used. It was parsed, required for an `app` or a `service`, and then dropped — the resolved project had no field to keep it in, so nothing downstream could tell which module the manifest meant. `ridge run` launched whichever module defined `main` first by name, which is the entry only by coincidence; an `entry` naming a file that was not in the project passed `check` and `build` in silence; and an app with no `main` anywhere compiled and then died at startup with a raw runtime dump. The declared entry is now the entry, an `entry` that names no module of the project is `M021`, and an entry module that declares no `main` is `M022` — both at check time, where the manifest and the sources can still be reconciled. A project that declares no entry, such as a library, keeps the rule it had.

- `T029` names the type it is talking about, wherever it comes from. Five places raised it and none of them named a type. Interpolating a value whose type has no `ToText` instance — `$"failed: ${e}"` on the error half of a stdlib `Result`, about as common as error handling gets — rendered the type through a printer with no access to the type table, so the message read `no instance ToText #12`, naming an internal constructor id. The other four sit in the constraint solver, on the ordinary path where a class method fails to dispatch, and they printed the internal representation outright: `no instance Sizeable TyConId(104)`, or `Con(TyConId(10), [...])`, or for a multi-parameter class the head as `TyConId(10) TyConId(3)` where it should read `Decimal Text`. The solver had the type table in hand the whole time — two of those sites look a declaration up a few lines earlier and then print the id anyway. All five now render the resolved type. The advice follows it: where the old note offered an instance for `T`, a placeholder from the message template rather than anything in the program, or asked for one "for this combination of types" without naming the combination, there is now a single note builder that names the class and the type and checks whether the reader can extend that type at all. One declared in the workspace can take `deriving` or an instance of its own; a built-in or standard-library type can take neither, since an instance written for it elsewhere is an orphan (`T031`), so for those the note says that rather than sending the reader to a second error — and for an interpolation hole it adds that printing a field of the value is the way out.

- Export patterns name modules, and are now matched as such. `[project.exports].public` is a glob over module names, and the import-visibility check has always read it that way — but the pass that marks which symbols leave the project compared the same patterns against bare symbol names, where a dotted module glob can never match. So `public = ["acme.domain.**"]` marked nothing as exported and reported itself as a typo (`M020`), once for every module in the project; only a bare `**` escaped, which is why the standard library's own `std.**` had been mismarked from the start. A module whose fully-qualified name matches an export pattern now has all of its `pub` symbols marked exported — the two layers of the visibility model, the manifest choosing modules and `pub` choosing symbols within them — and `M020` asks its question once per project, so a pattern that names nothing is still reported, once, as the typo it is. `exports_internal` is checked the same way; it was not checked at all.

- A manifest error reaches the user. Discovery is deliberately non-fatal — a project whose `ridge.toml` does not parse is skipped so the rest of the workspace still builds — but the errors it recorded were dropped on the way into resolution, so a workspace whose only project was skipped had no modules, no errors, and reported success: `ridge check` printed "Type-check passed" over a source it never opened, `build` reported "Compiled 0 module(s)", `test` found no tests, and all three exited 0. One typo in `allow` (`rand` for `random`) was enough. Those errors now travel with the workspace graph into resolution, so every command that renders diagnostics shows them, editors included. `ridge run` was a third instance of the same silent skip — a member whose manifest failed to parse vanished from the member list too, and the command answered `C006 NoExecutableMember`, pointing at the `kind` key on a manifest that declares it; it now names the manifest and the code its own parser assigned.

- A diagnostic with no source file renders as one line. Manifest and codegen-toolchain errors have no `.ridge` file to underline, and handing the renderer a source it cannot fetch made it print `Unable to fetch source` to stderr — twice, above the error it belonged to — and then draw an empty frame around a blank line. The headline now prints on its own, in the same shape the framed diagnostics use.

- `as` patterns build. Every `name @ pattern` — `one @ 1`, `admin @ Admin`, `found @ User { role }` — passed `ridge check` and then failed at `ridge build` with an `E004`, because the generated Core Erlang wrote the alias inner-first (`1 = V_One`) where the alias production is `variable '=' pattern`; `erlc` rejected the module and took the whole form with it. Nothing asserted what an alias printed, and no end-to-end test compiled one, so a documented pattern form was unusable in every program that reached for it.

- Exhaustiveness reads the field patterns inside a record pattern. Every record pattern used to count as matching every value of its type, however specific its fields were, so `match u` with the single arm `User { role = Admin }` passed `check` and then died on a `Guest` — and adding the `_` fallback that made it total was reported redundant, so following the advice deleted the only arm a `Guest` could reach. A record pattern is now irrefutable exactly when all of its field patterns are: `User { role }` and `User { .. }` still cover the whole type, `User { role = Admin }` covers one role, and `T016` names the case it misses. The same applies inside a record-payload union variant (`Login { userId = 0 }` no longer stands in for every `Login`), to the constructor-less form (`{ role = Admin }`), through nesting, and to a parameter binder — a refutable record pattern in a parameter is a `T043` the way a refutable pattern in that position always should have been. Witnesses render as patterns that parse: a record type reads `User { role = Guest }` rather than `User _`, and a nested one is parenthesised where it sits as a constructor argument.

- Actor `on` handlers and `init` blocks are now capability-checked the way top-level functions are. A handler whose body uses an effect it does not declare — `on increment = Io.println "hi"` with no `io` on the handler — is now a `T014`, and a call that exceeds the declared set a `T018`; before, handler and `init` bodies were never checked, so an undeclared effect escaped the actor's capability boundary (the union of its handlers' declared sets) in silence. `init` bodies are also type-checked for the first time — a mistyped state assignment such as `x <- "text"` into an `Int` field is reported at check time instead of slipping past it. A program that relied on the gap now has to write the capabilities it actually uses onto the handler or `init`, the declaration the capability model always required. The diagnostic's suggestion speaks each declaration's own syntax (`on {io} increment`, `init {time}`) rather than `fn`, and an inner `fn` whose annotation exceeds its enclosing function's set is told so in those terms instead of being misread as unannotated.

- A type annotation that named an imported standard-library type constructor applied to arguments — `Repo User MemAdapter`, `Query e a` — silently dropped its arguments and resolved to a fresh type variable, because the conversion only consulted the current module's own type names and treated an imported name as unknown. The arguments are kept now, so `let users: Repo User MemAdapter = ...` (and a function that returns one) pins the entity type as written rather than leaving it free to over-generalise. The visible symptom was a query that decoded into the wrong shape once a module derived `Row` for more than one record at a time.
- A function constrained over two instances of the same class — `where Row e, Row f`, the shape a pair decoder needs — forwarded the first instance's dictionary to every method call, so decoding the second value read the first type's fields and failed at runtime. Each call now forwards the dictionary for the type it actually produces, picked from that call's result type. The visible symptom was a two-table join's pair decode always erroring while the single-shape `select` worked.
- A few ordinary mistakes around union types reported an internal error (`T999`, "this is a compiler bug") instead of something useful. Using a type as a value constructor — the symptom of a single-variant union written without its leading `|`, which parses as a type alias — now reports `T044` with a hint toward the fix. Matching a record-style union variant, which isn't supported yet, reports `T044` as well. A genuinely unknown constructor is left to the resolver's `R010` rather than also raising `T999`.
- A type-class instance declared in one module over a builtin type — `instance Tag Int` in a library, called from another module — looked its instance dictionary up in the calling module rather than the module that declares the instance, so the call failed at load with an undefined function. The dictionary reference now resolves to the declaring module. Instances over a type defined alongside the instance were already correct; the gap was an instance over `Int`/`Text`/`Bool`/`Float` used across a module boundary.
- Deeply nested type and pattern syntax could overflow the native stack and abort the compiler with no diagnostic. The recursion-depth guard that already bounded expressions now covers types and patterns too, sharing one 256-level budget: a type such as thousands of nested `(((…)))` or `[[…]]`, or an equally deep pattern, stops at the limit and reports `P028` instead of crashing the process. No hand-written or formatter-produced program approaches the limit; only pathological or adversarial input does.
- `List.sort` and `List.sortBy` order by the element's (or key's) `Ord` instance now, not the BEAM's native term order. A union with a derived `Ord` sorts by its declared variant order — the reason to derive one — where before a `sort` fell back to however the tagged-tuple and bare-atom representations happened to compare, so a nullary variant could land ahead of a payload variant declared before it. Sorting primitives is unchanged (their `Ord` is the term order), sorting records by a field key such as `List.sortBy (fn u -> u.age)` keeps working through the key's `Ord`, and calling `compare` on a primitive resolves now where it previously could not find its instance dictionary. Both functions gained an `Ord` constraint on the element or key type.
- An exception crossing a function body that used `?` (or a non-tail `return`) was mangled instead of re-raised. The compiler wraps such bodies in a Core Erlang `try/catch` that re-raises anything it does not handle, but it passed the raw try tag where `erlang:raise/3` expects a stacktrace, so the re-raise itself failed and the function returned the atom `badarg` — a process that should have crashed, such as a `main` whose `?>` asked a dead actor, exited 0 in silence. The re-raise now fabricates a fresh stacktrace, preserving the exception's class and reason.
- The arithmetic operators (`+ - * / % **`) now reject concrete non-numeric operands at check time. They used to unify any two operands of the same type and lower straight to the BEAM's numeric BIFs, so `"a" + "b"` compiled cleanly and then crashed at runtime with `badarith`. The checker now reports `T052` and points at `++` for text concatenation. An operand whose type is still an unresolved variable stays accepted — pinning generic arithmetic to numeric needs a `Num`-style constraint the language does not have yet.
- A `main` that declares parameters is now rejected at check time with `T053`. The BEAM runner invokes the entry point with no arguments, so `pub fn main (x: Int) -> Unit` compiled cleanly and then crashed at startup with `undef` — and the code generator's own arity warning was inverted, annotating correct `main/0` programs while staying silent on the crashing shape. Command-line arguments are read through `Cli.args ()` from `std.cli`, which works under `ridge run` and inside an escript bundle alike.
- A standard library that fails to compile to BEAM now stops `ridge run` and `ridge test` instead of only warning. The driver printed that any program calling a Ridge-bodied stdlib function would die with `undef`, then started the program anyway, so the failure surfaced as an Erlang crash report rather than as the diagnostic that had already scrolled past. It reports `C010` and stops before launching the VM. `ridge build` keeps the warning and still produces artefacts — it hands them to a later step that can act on it, which is exactly what `run` and `test` are. The message also names the module that failed and what the toolchain said, rather than dumping the internal error struct.
- The `T053` hint now names the capability `Cli.args ()` needs. It pointed at `std.cli` for reading command-line arguments without mentioning that the call is `env`-gated, so following it verbatim landed in `T014`, and then `R016` once the signature was fixed but the manifest was not. The hint spells out both steps — `fn {env} main` and `"env"` in the manifest's allow-list. `Cli.args` was the only capability-gated function named in any hint; the rest (`List.at`, `List.forEach`, `Bool.not`, `List.length`, `++`) are pure and compile as printed.
- `ridge check` no longer appends a spurious `C001 NoWorkspaceRoot` line after reporting the real problem. When the check found diagnostics — or the driver itself failed — the command had already printed the actual errors, but then returned the wrong internal error variant, so the CLI's top level tacked on `error: C001 NoWorkspaceRoot: no workspace manifest found at or above the current directory` even though the workspace had been found and checked. A failing `ridge check` now prints only its true diagnostics and exits non-zero, the way `ridge build` and `ridge run` already behaved.
- A mistyped qualified name — `Io.printn "hi"` — no longer cascades into a `T999 internal type error` after the resolver's `R014`. The resolver already reports the unknown symbol with did-you-mean suggestions, but the type checker then looked the same name up in its own environment, missed, and piled on a `This is a compiler bug. Please report it.` — telling the user to file a bug over their own typo. The type checker now absorbs any qualified name the resolver has already accounted for, the same way it has always treated unresolved plain identifiers, so `R014` (or `R012`) is the only diagnostic.
- The release binaries now ship with `run --watch` and `run --reload` enabled. The release workflow built the CLI with only the `beam-runtime` feature, leaving `cli-watch` — the feature that gates watch mode and the hot-reload dev loop — off, so a `ridge` installed through `install.sh` rejected both flags with an error telling the user to rebuild from source. Hot-reload is a headline feature; installer users can actually use it now.
- Several diagnostics no longer leak compiler internals. Field access on a non-record — `xs.length` on a `List Int` — used to report `T006: with on non-record` with a raw unification dump (`found type #6 (#0)`), accusing the user of a `with` they never wrote; it now reports the new `T054` in field-access terms, renders the type as `List Int`, and suggests the module function (`did you mean List.length?`) when the type's constructor shares its name with a stdlib module that exports one. The genuine `with`-on-non-record `T006` keeps its code but renders its found type by name too. `T022 discarded result` printed the internal `Debug` form (`Var(TyVid(103))`); it now renders `List a`. Layout parse errors named the synthesised lexer tokens (`unexpected token <INDENT> in pattern position`, `expected <DEDENT> but found …`); they now say `indentation`, `end of block`, `line break`, and `end of input`. And the did-you-mean suggester no longer offers query-DSL internals — a typo one edit from `QAdd` used to be answered with `did you mean QAdd?`; the prelude's `Q*` constructors and query-builder projection types (`Ret`, `Rows`, `JoinCond`, …) are excluded from every suggestion path (`R010`, `R014`, `R008`).
- Longer diagnostics no longer break the frame they are drawn in. A message with an explanation and a `hint:` under its summary line was printed twice — once as the report title, once as the label beside the caret — and the newlines in the label escaped ariadne's margin, so the text spilled outside the gutter and the closing rule landed in the wrong column. The summary now goes beside the caret, the explanation renders as a note below the snippet, and the fix as a help, each inside the frame; an `Options:` list keeps its nesting. The error code stopped printing twice as well (`[T052] T052: …`), and a set of near-miss suggestions collapses into one line — `Io.printn` answers `did you mean \`print\`, \`println\` or \`eprint\`?` instead of drawing three arrows at the same span. Editors see the same cleanup: the code travels as its own LSP field, so it no longer appears again at the head of the message.
- Lexical errors no longer repeat the span as a raw byte range. A message ended with `at byte 66..67` — or `opened at byte 12..13` — right beside a snippet that already showed the same position as `line:column`, so the one part of the message a reader could not act on was the loudest. The span still travels structurally, which is what the renderer and the language server use; only the text lost it.

## [0.2.8] - 2026-05-29

### Added

- Multi-line string literals (`"""..."""`): triple-quoted strings strip leading indentation guided by the closing delimiter's column, drop the opening and closing newlines, and process standard escape sequences normally. The single-line `"..."` form is unchanged and still stays single-line.
- Raw string literals (`r"..."`, `r#"..."#`, `r##"..."##`): no escape processing; every byte between the delimiters is literal. Extra `#` pairs balance embedded quotes. Raw strings may span multiple lines without indentation stripping, complementing the cooked `"""` form.
- List patterns with rest: a single `..` in any position — `[first, ..]`, `[.., last]`, `[first, .., last]`. Bind the rest through the existing as-pattern operator: `[first, rest @ ..]`. At most one `..` per list pattern (`P024 MultipleRestInListPattern`); suffix and middle elements are restricted to bindings or wildcards in 0.2.8 (`L009`).
- Record patterns in `match`: a record-body pattern such as `User { name, age }` binds each named field, and a trailing `..` (`User { name, .. }`) matches the named fields while ignoring the rest. Naming an unknown field is an error, and omitting a field without `..` is reported as missing. The `..` itself cannot be bound.
- `@test "<name>"` attribute for marking test functions regardless of name or visibility. The string is the display name shown by `ridge test`. Return type is unchanged (`Result Unit Text`). When both `@test` and the `test_` prefix apply to the same function, the attribute wins and the test registers once.
- `ridge fmt --migrate-tests` rewrites `pub fn test_*` functions to the `@test` form in place. It inserts `@test "<derived-name>"` above each matching function without renaming it (derived name is the function name with `test_` stripped). The rewrite is idempotent — a function already carrying `@test` is left untouched.
- Design decisions covering the string literal syntax choices, rest pattern semantics, and test-attribute design are documented in `docs/spec.md §15`.

### Deprecated

- The `test_` function-name prefix for test discovery is deprecated (`C304 PrefixTestDeprecated`). Both `@test "<name>"` and `test_` continue to work in 0.2.x; the prefix is removed in 0.3.0. Use `ridge fmt --migrate-tests` to update existing test files.

### Resolved

- Open question Q-017 (multi-line and raw string literal syntax), carried since 0.1.0, is now resolved. See `docs/spec.md §16.1`.

## [0.2.7] - 2026-05-28

### Added

- Actors can now declare a `mailbox` configuration member alongside `state`, `init`, and `on`. Three forms are accepted: `mailbox unbounded` (the explicit default), `mailbox bounded N drop newest` (silently drop the incoming message on overflow), and `mailbox bounded N error` (raise `{mailbox_full, Pid}` in the sender on overflow, so a supervisor can decide what happens next). The capacity `N` is a positive integer literal; the overflow policy is mandatory when bounded, with `P022 MailboxPolicyMissing` if it is missing and `P023 MailboxBoundInvalid` if `N` is zero, negative, or out of range. The configuration keywords (`bounded`, `unbounded`, `drop`, `newest`, `oldest`, `error`) stay reserved only inside the `mailbox` member; everywhere else they remain ordinary identifiers. The historical unbounded default carries through unchanged when the member is omitted, so existing programs keep their behaviour byte-for-byte.
- New `std.actor` module shipping `Actor.mailboxSize : Handle a -> Option Int`. `Some n` is the queue length at the moment of the call; `None` means the actor is no longer alive. The function is cap-free: the handle itself is the proof of access, formalised in the new §6.4.1 "Handles as effect tokens" subsection. Reading the queue length is best-effort under concurrent senders — the value reflects what the next sender would see, which may briefly diverge from the strict bound under contention; the spec §7.2.1 documents this as a soft-bound invariant.
- Design decisions for the mailbox feature are collected into a new §15 of the spec, covering the syntax choice, the overflow-policy set, the let-it-crash semantics for `error` via `!`, the observability scope, and the "handle as effect token" capability rule that motivates the cap-free design.

### Changed

- The actor handle's runtime representation changed from a bare `Pid` to the opaque tuple `{ridge_handle, Pid, MailboxConfig}` so that `!` can honour the mailbox configuration carried by the handle without an extra dispatch hop per send. The Ridge surface is unaffected — the spec already treated `Handle a` as opaque — but any hand-written Erlang glue that assumed `is_pid(Handle)` needs to update to `is_tuple(Handle) andalso element(1, Handle) =:= ridge_handle`. The runtime exposes `ridge_rt:send_op/2` (the new target of `!`) plus `ridge_rt:mailbox_size/1` (read by `Actor.mailboxSize`) for direct integration paths. `ridge_rt:send/2` stays as a backward-compatible cast bridge for tooling built before this cut.
- `import` paths now accept the `actor` keyword as a module-path segment. The keyword stays reserved everywhere else; without this contextual exception, `import std.actor as Actor` collapsed silently to `import std` and `Actor.mailboxSize` at use sites failed to resolve. The change is purely additive — no existing import shape parses differently.

### Resolved

- Open questions Q-003 (actor mailbox size) and Q-014 (mailbox observability) from the 0.1.0 deferred-to-0.2.0 list are now closed. See `docs/spec.md §16.1`.

### Deferred

- The `drop oldest` mailbox policy is parsed but type-check-rejected (`T027 MailboxPolicyDropOldestNotShipped`); programs using it get a precise diagnostic listing the two policies that do ship. Implementing the policy needs a broker process intermediary because BEAM does not permit a sender to mutate another process's mailbox; it is deferred pending a broker implementation.
- The result-returning `Actor.send (h: Handle a) (msg) -> Result Unit MailboxFull` waits on first-class message values, which depend on the typeclass infrastructure not yet in scope. Until then `!` covers fire-and-forget and `bounded N error` surfaces overflow at the call site through a let-it-crash exit signal.
- `Actor.peek` and `Actor.drain` are deferred for the same reason — they require the message-shape typeclass infrastructure to be tipable. `drain` is additionally destructive and waits for a concrete use case before shipping.

## [0.2.6] - 2026-05-26

### Added

- `std.net.http` gains four web-hardening surfaces. `Http.sql raw` returns a `Sql` wrapper around a value with embedded single quotes doubled (`'` -> `''`); `Http.html raw` returns an `Html` wrapper around a value with the five HTML special characters (`&`, `<`, `>`, `"`, `'`) escaped to entity references, with `&` processed first so existing entities double-encode predictably. Both are pure (no capability). The newtypes are records with a single `value` field; pattern matching is via field access. Direct record-syntax construction (`Sql { value = "..." }`) is technically possible but bypasses the escape pass — the type wrappers are a hint to the type checker and to code review, not a runtime-enforced boundary. The SQL escape is not a substitute for parameterized queries, and the doc comment says so.
- `std.net.http.SecureCookie` record + the `Http.secureCookie name value` factory. The dispatch is opt-in by naming: no new syntax, no global typeclass table. The closed `ToText` set (Int / Float / Bool / Text / Timestamp) keeps its existing path; user types now get a third path that synthesizes a `Call(External, toText, [arg])` to the type's owning module. ## [0.2.5] - 2026-05-25

### Fixed

- Multi-step type alias chains now resolve all the way to their terminal body. `type IntList = List Int` followed by `type Numbers = IntList` used to leave `Numbers` interned as `Type::Con(IntList, [])` because pass 2 of user-tycon collection reads `ctx.tycon_decls` before that table has been synced from the arena, so every later alias saw its earlier siblings only as their pass-1 placeholders. A dedicated third pass walks every alias body after pass 2 and expands any embedded `Type::Con(alias_id, args)` to the alias's resolved body, chasing through the chain until it lands on a non-alias terminal type. A visited set breaks cycles defensively.
- Parametric type aliases (`type Stack a = List a`, `type Pair a b = (a, b)`) now substitute through to their bodies at every use site. The previous shape `TyConKind::Alias(Type)` held only the body, with no record of the alias's own type-parameter vids, so `Stack Int` at a use site fell through to an opaque `Type::Con(Stack, [Int])` that never unified with `List Int`. `TyConKind::Alias` now carries `{ params, body }`; the body keeps the alias's parameters as `Type::Var(p_i)` placeholders and use sites substitute them with the call-site argument types before wrapping in `Type::Alias { name, body }`. The chain pass also substitutes when crossing parametric aliases, so `type Stack a = List a; type IntStack = Stack Int` resolves `IntStack` directly to `List Int` at collection time.

### Added

- `Text.slice (start: Int) (len: Int) (s: Text) -> Text` extracts a substring counted in grapheme clusters, completing the text-API set that already shipped `byteSize`, `length`, and `join`. Indexing follows the rest of the text surface (graphemes, not bytes), so `slice 0 2 "café"` is `"ca"` and `slice 3 1 "café"` is `"é"`. Both bounds saturate — a start past the end gives `""`, a length larger than what remains returns the tail, and negatives clamp to zero, so arithmetic results can be passed without guards. Bridged through `ridge_rt:text_slice/3`, which wraps `string:slice/3`.

### Changed

- `ridge test` now prints per-test results live as workers finish, with an `[N/M]` prefix aligned to the width of `M`. Long suites no longer look frozen until the last worker joins. Output stays in input order — the same deterministic shape CI logs depend on — because each worker drains a shared print cursor and only prints contiguous-ready outcomes from there forward; the worker that finishes the next head-of-queue test takes over the drain. The tally now reads from atomic counters incremented at print time rather than a post-scope iteration.

### Fixed

- `ridge run` now aborts when the compile pipeline emits error-severity diagnostics instead of silently launching the BEAM module on top of stale artefacts. When a project's `[capabilities].allow` list omitted a capability the source actually used (for example `Io.println` against `allow = []`), `ridge build` correctly emitted `R016` but `ridge run` re-executed a `.beam` left over from a previous good compile, bypassing the capability contract declared in `ridge.toml`. Two bugs were blocking this: the parser's type-body disambiguation only looked one token ahead, so a `|` beyond the first constructor's arguments caused `P002 expected top-level decl`; and the lowering pass wrapped a union constructor call in `IrExpr::Call` instead of folding the arguments into the `IrExpr::Construct` node, which made the BEAM crash with `{badfun, 'Circle'}`. ## [0.2.3] - 2026-05-24

### Fixed

- Unresolved identifier errors no longer ship with a misleading `T999 internal type error / This is a compiler bug. Please report it.` companion. The typechecker used to re-report any `Expr::Ident` that the resolver had already rejected, framing a known unresolved-name as a compiler invariant violation; for users hitting `not x` or any other shadowed-prelude shorthand, the screen showed both a clean `R010` *and* a "report a bug" message about the same name. The typechecker now absorbs the unresolved-Ident silently — the resolver's `R010` (with its suggestion list) is the canonical user-facing diagnostic for that path.
- The "did you mean?" list for an unresolved identifier now leads with the well-known prelude-shorthand a developer most likely meant. Bare `not`, `and`, `or` get `Bool.not` / `Bool.and` / `Bool.or` ahead of the Levenshtein-noise suggestions; bare `print` / `println` get `Io.println`. The base Levenshtein candidates still follow. Previously the suggestion list for `not` was `Int / Io / Set` — none of them helpful, and the qualified `Bool.not` was too far away in edit distance to surface.
- `P009 non-associative chain` no longer fires on `(arith) <comparison> rhs` expressions such as `a + b == c` or `acc + rej != total`. The chain detector compared `non_assoc_level(prev_op)` against `non_assoc_level(op)`, but `non_assoc_level` ignored its argument and returned `0` unconditionally — so any `Binary` left-hand side followed by a non-associative comparison reported `P009`, with a misleading "operator `!=` cannot be chained" message that pointed nowhere near the actual code. The detector now requires the previous op to itself be non-associative before applying the level check; legitimate chains like `a == b == c`, `a < b < c`, and the cross-level `a < b == c` continue to error.
- `Text.replace from to s` now replaces every occurrence of `from`, not just the first. The public bridge in `crates/ridge-stdlib/stdlib/text.ridge` used to call `binary:replace/4` with an empty options list, which Erlang interprets as first-occurrence-only; the function name promises global semantics and matches what users coming from Python's `str.replace`, JavaScript's `replaceAll`, Rust's `str::replace`, or Go's `strings.ReplaceAll` expect. The bridge now routes through `ridge_rt:text_replace_all/3` (which already passes `[global]` and is the same shim used by `Text.split`), so the canonical pipeline `s |> Text.replace "\n" " " |> Text.replace "\t" " "` collapses every newline and every tab as intended. Two regression tests pin the multi-occurrence and pass-through cases.
- `Net.Http.get` / `post` / `put` / `delete` now work end-to-end against HTTPS URLs and real-world APIs. Three bugs in the client path were resolved together in `ridge_rt`:
  - `application:ensure_all_started(ssl)` is invoked alongside `inets`, so the first `https://` request no longer crashes with `{failed_connect, [{inet, [inet], ssl_not_started}]}`.
  - The success path returns `{ok, #{status => …, body => …}}` and the error path returns `{error, #{code => …, message => …}}` — atom-keyed maps that match the Ridge `Response` and built-in `Error` records. The previous wire emitted `{response_record, S, B}` and `{error_record, C, M}` tagged tuples, which crashed any caller touching `resp.status` or `e.message` with `badmap`. (Same root cause as the `http_listen` server-side fix in 0.2.2.)
  - A default `User-Agent: ridge-lang/0.2` header is sent on every request. `httpc`'s built-in `User-Agent: httpc/X.Y` is rejected by several production APIs (GitHub returns HTTP 403 "User-Agent header required"), so the default would not get a beginner past their first real call. Custom headers remain deferred per the std.net.http scope guard.
- 0-arity stdlib symbols used as a value (not a call) now lower to a direct `M:F()` invocation instead of being wrapped in a `fun () -> M:F() end` thunk. `Map.empty`, `Set.empty`, and `List.empty` are typed as values (`Map k v`, `Set a`, `List a`) but the codegen always emitted a function reference, so `state table = Map.empty` leaked the fun into the state map and `Map.size Map.empty` crashed with `badmap`. The lowering now short-circuits the zero-arity case; higher-arity stdlib references continue to receive the fun wrapper they need to round-trip through `apply/2`. Bare `state table = Map.empty` is the idiomatic form again.
- `Text.split "" str` returns the list of graphemes in `str` instead of crashing the BEAM with `badarg`. The bridge delegated straight to `binary:split/3`, which rejects an empty pattern; the runtime shim now branches on `<<>>` and walks the input via `string:next_grapheme/1`, rebuilding each cluster as a UTF-8 binary so multi-byte characters survive. `Text.split "" ""` is `[]`. Two stdlib tests pin the empty-separator and empty-input cases.
- 0-arity stdlib bridge calls no longer trip on the dummy `Unit` argument the parser inserts for `f ()` calls. PR #71 dropped the surplus `Unit` for local 0-arity functions but missed the stdlib bridge path, so `Map.empty ()`, `Json.jNull ()`, and any other `0-arity stdlib ()` form was rejected with `E001 expects 0 args, got 1`. The codegen's `lower_call_to_stdlib` now checks the bridge target's arity and drops a single `Unit` argument when the target takes none — the symmetric counterpart to the local-fn shim. All four `BridgeTarget` variants benefit (`BeamStdlib`, `Perm`, `RidgeRuntime`, `RidgeStdlibLocal`).
- State-field defaults that fail to lower no longer silently drop the field. `lower_init_body` filtered codegen errors through `.ok()` and quietly continued with the surviving fields, so any `state X = expr` whose `expr` couldn't lower (`Map.empty ()` before the PR above, for instance) produced an init that omitted `X` entirely, and the next `maps:get(X, V_State)` crashed with `badkey: X` far from the real failure. The lowering now propagates the underlying `CodegenError` with `?`, so the user sees the actual diagnostic at compile time.
- `http_listen` parses requests and emits responses as atom-keyed maps (`#{method =>, path =>, body =>}` / `#{status :=, body :=}`) instead of tagged tuples, matching the wire shape that Ridge records lower to. Handlers can now read `req.body` and return `Response { ... }` without the runtime falling through to its `bad response: ...` 500 fallback. Validated end-to-end against `http-echo`: `curl -d "round trip" :18181/` round-trips POST / GET / DELETE bodies as expected.
- The `with`-peephole optimisation no longer rewrites a user-named record-literal RHS as a `with` update when the field reads point at a *different* record type. `forwarding_base` used to accept any local variable, so `Response { status = 200, body = req.body }` (Request → Response) was collapsed into `req with { ... }` and the type-changing field assignments silently lost — `body` ended up dropped because the peephole assumed no-op. The check now requires the base local to be one of the synthetic `__with_base_N` locals that Phase-5 `with`-lowering emits, restricting the optimisation to its intended subject. A dedicated test reproduces the http-echo shape.
- `std.net.http.respond status body` lowers to the two-argument bridge call it declares instead of being treated as a single-argument identity. The codegen had a hard-coded shortcut that assumed `respond` was a 1-arg wrapper and emitted `E001 expects 1 arg, got 2` for the canonical `respond 200 req.body` form. The shortcut is gone; the call now resolves through the bridge map, which already points at `std.net.http:respond/2`. Two tests cover bridge resolution and the full-pipeline lowering.

- `Float.parse` returns `None` instead of crashing the BEAM with `badarg` when handed an integer-shaped string like `"100"`. The wrapper now goes through `ridge_rt:float_parse/1`, which tries `binary_to_float/1` first and falls back to `float(binary_to_integer/1)` before reporting `None`.
- T017 `RedundantPattern` no longer fires on arms that carry a `when` guard. The exhaustiveness algorithm in `crates/ridge-typecheck/src/exhaustiveness.rs` now skips guarded arms in both the T016 coverage matrix and the T017 prefix matrix, matching Maranget's algorithm. The previous behaviour rejected every canonical guarded `match` (e.g. `match n { m when (m % 15) == 0 -> "FizzBuzz" ; m when (m % 3) == 0 -> "Fizz" ; ... }`) as redundant.
- Non-BIF calls in `when` guards no longer make `erlc` reject the generated Core Erlang. Guards that contain calls outside the BEAM guard-BIF whitelist — e.g. `m when (m % 15) == 0`, which lowers through `std.int:mod/2` — are lifted out of clause-guard position into a nested `case` chain. The whitelist now matches the OTP reference manual exactly, so non-guard `erlang:*` functions (`integer_to_binary`, `list_to_binary`, …) that previously slipped past the loose `module == "erlang"` check are correctly routed through the lift path too.
- Actor handlers invoked via `!` (cast) no longer drop the side-effecting expressions in their body. `lower_handler_body_for_cast` ignored the leaf value when wrapping the `{noreply, V_State}` tuple, so every `Io.println`, `partner ! msg`, and non-assign call disappeared from `handle_cast/2` (state mutations survived because they thread through `V_State<n>` SSA). The wrap now sequences the leaf via `Do { first: val, then: noreply }`, mirroring the `?>` (ask) path.
- `partner ! handler arg1 arg2` now sends `{handler, arg1, arg2}` instead of `{''}`. The lowering of `Expr::Send` only recognised a bare `Expr::Ident` as the handler name and hard-coded `args: Vec::new()`, so every send with arguments emitted an empty 1-tuple that no receiver could pattern-match against. `unfold_send_message` peels the `Call { callee: Ident, args }` shape the parser produces and propagates the args through `IrExpr::Send`.
- Reads of an actor state field that follow a `<-` assign in the same handler invocation now see the new value. Before, `count <- count + 1; Io.println $"count = ${count}"` lowered the second `count` against the pre-assign `V_State`, so the print reported the stale value; the `received == N` checks in collector-style actors silently never matched. Codegen now tracks the current state SSA index on the local scope and retargets `IrExpr::Local { name: "__state" }` to the latest `V_State<n>` after every assign, propagating the per-arm result back to the outer scope after a `Match`.
- `ridge run` streams the BEAM program's stdout to the terminal as it is produced instead of buffering the whole pipe and dumping it at exit. Long-running programs, anything with a `Time.sleep`, and any non-trivial actor flow previously looked like a hang followed by a single output dump. Stdout is now inherited; stderr stays piped so `RunError::ErlExitNonZero` can still surface BEAM crash dumps and warnings.

### Refactor

- `lift_guarded_match` hoists the remaining-arms expression into a `let V_LiftedRest<depth> = fun () -> <rest> end` thunk and replaces the duplicated fall-through references with `apply V_LiftedRest<depth> ()`. The previous shape cloned the rest into both the guard-case wildcard and the outer wildcard, so a chain of `N` lifted arms produced `2^N` copies of the deepest fall-through body.
- Stdlib per-tier scratch workspaces are managed by `tempfile::TempDir`. The directory is removed on every `compile_tier` exit (success, `Err`, or panic), eliminating the `/tmp/ridge_stdlib_tier*_<pid>/` orphans that the old manual cleanup left behind whenever discover, resolve, typecheck, or lower returned `Err`.

### Docs

- `docs/tutorial.md` Troubleshooting section gains a Windows entry covering `chcp 65001`. `Io.println` writes UTF-8 to stdout, but the default Windows console codepage is `cp1252` on most English/Spanish installs, so non-ASCII output rendered as mojibake (`°` → `Â°`, `é` → `Ã©`). The new entry documents both the per-session `chcp 65001` and the system-wide *Use Unicode UTF-8 for worldwide language support* toggle.

### Internal

- `crates/ridge-driver/tests/integration.rs` serialises the five `erl`-touching tests behind a module-level `Mutex` so the PATH-clearing `run_missing_erlang` test no longer races with parallel siblings that spawn `erl`. The earlier workaround — moving the related test to its own binary file — stays in place as defence-in-depth.

  package. Extension version bumped from `0.1.0` to `0.2.0` to track the
  language release. Extension README rewritten as a Marketplace listing.

### Changed

- **BREAKING:** Source-file extension renamed from `.rg` to `.ridge`. Resolves a registry collision with Rouge on GitHub Linguist and avoids ambiguous syntax highlighting on github.com. Both `install.sh` and `install.ps1` now derive the version they validate against from `RIDGE_VERSION` (release-download path) or from `Cargo.toml` (cargo-install path). - `install-smoke.yml` gains `pull_request` (paths-filtered to `tools/install/**`, `Cargo.toml`, `Cargo.lock`, and itself) and `workflow_dispatch` triggers so install-script changes validate on Linux, macOS, and Windows before merging instead of only at release-publish time.

## [0.2.0-rc4] - 2026-05-18

Release candidate adding Sigstore keyless signing for release artifacts and
opportunistic signature verification in the install scripts. Integrity guarantees
remain SHA256-anchored when `cosign` is unavailable.

### Added

- Sigstore keyless signing in `release.yml`: every release archive is signed with `cosign sign-blob --yes --bundle`, producing a `.cosign.bundle` sidecar (signature, certificate, and Rekor transparency-log entry) uploaded next to the archive and its SHA256
- `install.sh` and `install.ps1` opportunistically download the `.cosign.bundle` and, when `cosign` is on PATH, verify it with `cosign verify-blob` pinned to the `ridge-lang/ridge` release workflow identity and the GitHub Actions OIDC issuer
- "Verifying release signatures manually" section in `tools/install/README.md` with the full `cosign verify-blob` recipe

### Security

- Release artifacts are now cryptographically signed and logged to the Rekor public transparency log, providing tamper-evident provenance in addition to SHA256 integrity
- Installer pins the verification identity to `https://github.com/ridge-lang/ridge/.github/workflows/release.yml@refs/tags/v*` and the OIDC issuer to `https://token.actions.githubusercontent.com`, so a signature minted by any other workflow or fork is rejected

### Changed

- New advisory codes in the installer output: `R055` when `cosign` is not on PATH (signature check skipped, SHA256 still enforced) and `R056` when `cosign verify-blob` fails (installation aborts)
- `release.yml` job permissions now include `id-token: write` so the runner can mint the OIDC token Sigstore exchanges for a short-lived signing certificate

## [0.2.0-rc3] - 2026-05-18

Release candidate cut to align release artifacts with the install-script
fixes landed in rc2. The rc2 binaries predated `ridge-lsp --version`,
which broke the cross-platform install-smoke verification.

### Added

- Install-smoke CI workflow validating `install.sh` / `install.ps1` end-to-end on Ubuntu, macOS, and Windows on every published release
- `ridge-lsp --version` flag for parity with `ridge --version`
- Post-install verification: both installers now confirm `ridge-lsp` and `ridge` report matching versions

### Fixed

- `install.sh` no longer exits silently when invoked via `curl … | sh` in CI. Root cause: the script's Erlang prerequisite check (`erl -noshell -eval …`) reads stdin, and when bash itself was reading the script from stdin, `erl` consumed the still-unread bytes and bash hit EOF before printing anything. Smoke workflow now downloads to a file and runs `bash -x` on it.
- `install.ps1` `exit N` calls inside `iex`/scriptblock no longer kill the host PowerShell session. Refactored to `throw` + `return` wrapped in `& { ... }` with try/catch that propagates `$LASTEXITCODE`.
- `install.ps1` no longer fails under `iwr | iex` due to `param()` blocks or UTF-8 BOM. Options now come from env vars (`$env:RIDGE_DRY_RUN`, etc.) and the file is BOM-free.
- macOS x86_64 release artifact builds via cross-compile from the `macos-14` (M1) runner instead of the deprecated `macos-13` image
- Windows install: `ridge-lsp.exe` extraction no longer fails when an existing VS Code LSP child has the binary locked (pre-flight stop + `Test-WriteAccess`)

## [0.2.0-rc1] - 2026-05-17

Initial public release candidate.

### Added

- Typed functional language for the BEAM with Hindley-Milner inference and row polymorphism
- Nine first-class capabilities (`io`, `fs`, `net`, `time`, `random`, `env`, `proc`, `spawn`, `ffi`) visible in every function signature
- Actor-first concurrency with mutable state confined to actors
- Compiler to BEAM bytecode via Core Erlang
- LSP server with diagnostics and correct file attribution
- Command-line tooling: `ridge run`, `ridge test`, `ridge fmt`, `ridge repl`, `ridge new`
- Workspace model with `git` and `path` dependencies
- VS Code extension (TextMate grammar + LSP client)
- Standard library: `bool`, `cli`, `env`, `float`, `fs`, `int`, `io`, `json`, `list`, `map`, `net.http`, `option`, `proc`, `random`, `text`, `time`
- Apache-2.0 licensed
